# Уведомления координатора о статусе и назначении задачи: B-07

v1/legacy смена статуса сохраняет actor ID/name, version, новый status и снимок Telegram-привязки координатора вместе с task/history/audit/outbox в одной транзакции. Инициатор не получает уведомление самому себе. Назначенный core/faculty исполнитель либо admin — автор действия; координатор задачи — адресат. Выполнение общей задачи остаётся shared, имя фактического инициатора сохраняется.

Обрабатывается только `task.status`: `assigned`, `waiting`, `in_progress`, `completed` и `open`, когда доменная команда допустима. Отмена подключена отдельной `task.cancel`: [task-comment-cancel-delivery.md](task-comment-cancel-delivery.md). Исторические источники без полного снимка завершаются failed, без угадывания автора/адресатов из текущей БД.

## Переиспользованный поток

V019 расширяет существующий `task_manual_intents.action`, добавляя status и snapshot `task_status` с DB CHECK. `TaskManualPlanner` материализует source в `category=task_status`, сохраняя maintenance → task/source locks, SKIP LOCKED, атомарность, dedupe и общий sender. Исторические имена planner/таблицы сохранены; второй очереди, transport или зависимости не добавлены.

Audit подтверждает actor/action/version. Перед материализацией и снова перед HTTP проверяются текущие version/status, registered/active actor, право исполнителя на задачу (включая faculty/all membership) либо admin; при completed фактический completed_by должен совпадать с инициатором. Адресат должен оставаться текущим активным зарегистрированным core-координатором задачи с той же положительной Telegram-привязкой. Перед сетью проверяются также action/category/source/intent/expiry/lease; смена координатора не перенаправляет старый snapshot.

Срок — 15 минут от исходного available_at; future source раньше срока не потребляется, stale/removed/cancelled не отправляется. Последняя версия имеет приоритет: новое действие блокирует ещё не отправленное сообщение предыдущей версии, но не отзывает уже подтверждённое. Completed source означает материализацию, не Telegram delivery. Повтор HTTP/source не переиздаёт sent/unknown; unknown автоматически не повторяется.

Сообщение тихое, plain text: название задачи, понятный статус и имя инициатора. Описание, ТЗ и приватный completion comment не передаются. Форматирование/кнопки — финальный CHAT-01/B-08. Общие quota/lease/retry остаются прежними, HTTP вне транзакции. Реальные отправки выключены.

## Взятие и отказ: уведомления координатору

Команды v1/legacy claim/release в общей транзакции сохраняют задачу, аудит и task.claim/task.release с frozen Telegram snapshot координатора (creator), кроме самого инициатора. Первоначальная приёмка этого блока покрывала координатора; расширение admin/open аудитории описано ниже. V021 расширяет существующий audited intent action и CHECK формы task_status; category=task_assignment, общий TaskManualPlanner/TaskDeliveryGate/queue/sender. Новая очередь/отправитель/зависимость не добавляются.

Сообщение тихое, plain text: «Задача взята в работу» либо «Исполнитель отказался от задачи», название и имя инициатора. Без description/ТЗ/комментариев. До HTTP повторно проверяются текущие версия/status, активность/регистрация инициатора, core/faculty роль и scope, frozen/current coordinator и его Telegram binding. Claim требует сохранённое назначение инициатору, core scope и текущую подходящую компетенцию; release — отсутствие его назначения и действующее faculty membership для faculty/all. Коллеги остаются назначенными; последний отказ переводит задачу в open. Последующая версия отменяет устаревшее уведомление. Недоступный target — unavailable; malformed/legacy без snapshot или без matching audit отвергается.

Материализация атомарна, два planner не создают дублей. HTTP replay возвращает прежний результат; source completed не означает sent. DB-clock due и 15-minute expiry, lease/quota, rollback и unknown без автоматического replay сохраняются. HTTP вне транзакции; production sender выключен. Форматирование/кнопки оставлены CHAT-01/B-08.

Граница первоначального блока — координатор. Существующий Node дополнительно уведомляет admins о claim и команду при возврате на доску; перенос этих аудиторий описан ниже с согласованным competency filter вместо прежней широкой рассылки. Callback acknowledgement и Telegram consumer относятся к B-08, текущая реализация покрывает HTTP v1/legacy.

Приёмка 04.10.2026: полный mvnw.cmd --batch-mode verify — **252 tests, 0 failures/errors/skipped, BUILD SUCCESS**, PostgreSQL 17.11 и V021 на чистой БД; log target/task-assignment-verify.log. Восемь новых интеграционных сценариев покрывают обе команды/replay/fake send вне TX, multi-assignee/status safety, version/actor/reversal/coordinator/binding gates, competency denial/revocation, self/faculty/all membership, malformed/unaudited/future/expired/unavailable, atomic rollback/two planners/unknown и legacy replay с latest-version suppression. Прежние 244 зелёные, diff check чистый. Блок координатора 100%; B-07 оценочно 73%, общий план 38/65 (58.5%). Реальный Telegram/SLO/production cutover это не подтверждает.

## Дополнительные адресаты claim/release

Claim фиксирует активных зарегистрированных admins, кроме инициатора, вместе с координатором. Если координатор сам admin, ему создаётся только одна доставка. При последнем release открытой core-задачи добавляются активные зарегистрированные core-участники с хотя бы одной требуемой компетенцией; без требований — вся core-команда, кроме инициатора. Координатор остаётся отдельным адресатом уведомления об отказе, независимо от компетенции, и не получает второй open notice. Частичный отказ и faculty/all не создают широкую рассылку. Это намеренно более узкая аудитория, чем старый Node release.

Каждый frozen recipientSnapshot фиксирует kind: coordinator/admin/open. Planner проверяет вид адресата и форму события; перед materialization/HTTP нужны текущие права именно этого вида. Admin после снятия роли не может получить старое admin-уведомление как новый координатор; бывший координатор не становится автоматически участником open-аудитории. Open требует актуальную компетенцию, core role, status=open и отсутствие любых назначений. Новые admins/участники/компетенции после команды аудиторию не расширяют; текущие version/actor/binding/expiry/lease gates сохраняются. Источники assignment без kind отвергаются, готовые доставки без kind блокируются, не дополняются текущими данными.

Для open адресата текст «Задача снова свободна», название и имя инициатора; для координатора — факт отказа, для admins claim — факт взятия. Тихие plain-text сообщения без описания/ТЗ/комментариев; форматирование CHAT-01 остаётся последним. Общий task_assignment/intent/dedupe/queue/sender сохранён, новая миграция не нужна. Ponytail: один openCoreAudience используется созданием/правкой/последним отказом, без второй реализации competency selection или новой зависимости. Обе аудитории материализуются атомарно; rollback/two workers/unknown и выключенный production sender сохраняются.
