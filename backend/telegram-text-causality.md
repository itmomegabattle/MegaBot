## Existing boundary

`TelegramInboxQueue` serializes persisted reception order and lease recovery per chat. It cannot recover unknown/late Telegram history. Current meeting mutations require a committed SENT canonical prompt, current owner/profile/revision/binding and fixed15-minute TTL. These checks establish current authority, but do not prove that an incoming text was written in response to that prompt. A delayed text can otherwise be interpreted as a later dialog field. Do not mark reordered policy accepted or enable a consumer from the existing tests.

## Primary API findings

- [Update](https://core.telegram.org/bots/api#update): update IDs increase sequentially, with a random next identifier after at least a week without updates. This is not a complete causal link between a human message and an outgoing prompt.
- [Message](https://core.telegram.org/bots/api#message): message IDs are documented as unique within a chat. Do not infer a stronger chronological guarantee merely from numeric comparison.
- [ReplyKeyboardMarkup](https://core.telegram.org/bots/api#replykeyboardmarkup): optional `force_reply` requests the native reply interface while keeping keyboard rows. The project's shared parser now accepts its canonical true form alongside the unchanged default shape; false/null/non-boolean and unrelated fields fail closed. Local HTTP roundtrip and existing delivery integration tests cover the field; native handset acceptance is still a release gate.
