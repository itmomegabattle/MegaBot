# Уведомления о встречах: B-07

Создание, изменение и отмена `meeting/setup/vibe` проходят весь серверный путь: HTTP-команда → transactional outbox → неизменные адресаты → общая очередь → domain gate → sender. Sender по умолчанию выключен; production и реальные сообщения этим изменением не затронуты.

## Снимок и материализация

Команда сохраняет actor, version, предыдущую/новую аудиторию, Telegram ID адресатов и текущие важные group/topic bindings вместе с встречей, audit и Calendar job. Planner проверяет соответствующий audit, действующего автора и последнюю версию встречи. Completed source означает только материализацию, не Telegram-доставку. Intent, targets и deliveries фиксируются атомарно; rollback и повторный проход не создают дублей. Два workers используют PostgreSQL SKIP LOCKED.

Личные targets: текущие приглашённые; при правке также исключённые из предыдущей аудитории. Получатель должен оставаться активным зарегистрированным core-участником с той же Telegram-привязкой. Исключённый получает только сообщение об исключении и **прежнее название**, без нового названия, времени и описания. Новые участники вне снимка автоматически не добавляются.

Групповой target требует точного совпадения numeric bot ID, отрицательного chat ID и положительного thread ID с текущей привязкой «ВАЖНОЕ». Новая привязка не расширяет снимок; смена топика запрещает старую доставку, не перенаправляет её. Production claim дополнительно проверяет bot ID настроенного отправителя. Legacy binding с bot ID `main` не преобразуется автоматически: numeric identity нужно согласовать при B-08/B-09.

Срок действия — 15 минут от исходного available_at; для создания/правки не позже окончания встречи. Отложенный source раньше due не материализуется. Старые версии и отменённые намерения не отправляются. Legacy source без полного снимка завершается безопасной ошибкой, без восстановления адресатов из изменяемых текущих данных.

## Перед сетью и результат

Gate повторно проверяет version/status встречи, audit-автора, состояние source/intent, срок, личное приглашение либо исключение, роль/активность/Telegram-привязку и group/topic binding. Важный топик имеет приоритет перед личными targets при одинаковом available_at. Это не обходит общую bot/chat quota.

Текст пока простой, без описания, Markdown и RSVP-кнопок; уведомления встреч не silent, как в прежнем контуре. HTTP выполняется вне DB-транзакции. Retry/429, leases, expiry и unknown используют существующую [очередь](notifications.md) и [sender](dispatcher.md). Unknown автоматически не повторяется; completed source не переиздаёт доставку после сетевой ошибки.

## Предвстречное напоминание

По согласованию с владельцем — за **1 час**. `MEETING_REMINDER_MINUTES=60` (0 отключает создание новых напоминаний, допустимо 0…1440). Создание и изменение встречи записывают будущий `meeting.reminder` в той же транзакции, что встречу, приглашения, audit и Calendar job. Отдельного scheduler/worker нет: используется существующий planner и общая очередь. Calendar job по-прежнему один на команду и не содержит reminder action.

Снимок адресатов и групп неизменяемый; исключённые из встречи не получают напоминание. Проверяются audit исходной команды created/updated, версия, текущие права, приглашение и точная Telegram/group/topic-привязка. RSVP не меняет список приглашённых: напоминание адресуется всей приглашённой аудитории. Новая версия заменяет старую логически, без переотправки sent/unknown. Старые будущие источники будут безопасно завершены при наступлении их due.

Обработка не начинается раньше due по часам БД. При простое допускается догоняющая отправка в пределах 15 минут, но никогда после начала встречи; gate перепроверяет начало прямо перед HTTP. Если встречу создали/перенесли менее чем за час, прошедший reminder due не восстанавливается: остаётся обычное уведомление о создании/правке. Уже существующие встречи без reminder source автоматически не пополняются; backfill требует отдельной согласованной миграции. Изменение интервала влияет только на последующие команды, не передвигает уже сохранённые due.
