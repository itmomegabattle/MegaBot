# Задачи: контракт B-06

Режим `shared`: один статус на задачу, завершение сохраняет фактического `completedBy`. Команды блокируют строку `tasks FOR UPDATE`, проверяют права и `expectedVersion`, затем фиксируют задачу, историю, audit и outbox в одной транзакции. HTTP-запросы к Telegram не выполняются. Все события задач содержат `disableNotification=true`; завершение адресуется автору задачи.

## Переходы

| Исходный статус | Допустимые следующие статусы | Условие |
|---|---|---|
| open | assigned, cancelled | assigned — атомарный claim или назначение автором/admin |
| assigned | open, in_progress, waiting, completed, cancelled | open — снято последнее назначение |
| in_progress | open, assigned, waiting, completed, cancelled | open — снято последнее назначение |
| waiting | open, assigned, in_progress, completed, cancelled | open — снято последнее назначение |
| completed | assigned, in_progress, waiting, cancelled | переоткрывает исполнитель/admin; отменяет автор/admin |
| cancelled | нет | старая кнопка не возобновляет задачу |

Повтор текущего статуса — no-op после проверки прав. Отмена отдельной командой идемпотентна; `status=cancelled` в общей status-команде не принимается. Изменение результатов завершения требует явного переоткрытия. `release` снимает только текущего исполнителя; назначения коллег остаются. У открытой задачи нет исполнителей, у остальных рабочих статусов должен быть исполнитель.

## Доступ и время

Создавать задачи может core-команда. Редактирование и отмена доступны автору или admin. Статус меняет исполнитель или admin. Claim основной задачи требует пересечения компетенций, если они заданы; факультетская задача назначается core-координатором. Faculty видит задачу только при совпадении факультета и наличии собственного назначения. Его комментарии ограничены собственным авторством/target, заметки другим исполнителям не выдаются.

Дедлайн передаётся календарной датой и сохраняется как `23:59:59.999 Europe/Moscow`. Архивирование мероприятия не фильтрует незавершённые задачи. Существующая привязка к архивному мероприятию сохраняется; новое назначение архивного event запрещено.

Все mutations требуют `Idempotency-Key`; append-only комментарий благодаря ключу не дублируется при повторе. Чтение списка и истории поддерживает cursor/limit, максимум 100. Для списка cursor — последний `id`; для истории — последний `id` записи в хронологическом порядке. Для следующей страницы передаётся последний ID полученной страницы.

## Граница B-06 и следующих этапов

Домен задач и все task/faculty-task HTTP routes из parity matrix реализованы в Java. Предпросмотр/очистка/сброс используют один recovery-контур; ручное напоминание транзакционно сохраняет намерение доставки. Проверки B-06 выполняются на PostgreSQL/Testcontainers, не вместо БД и не с незаметными пропусками.

Фактический worker, occurrence, lease/retry/unknown и точность времени отправки — B-07/TIME-01…07. Telegram callbacks и живые Telegram/Google проверки — B-08. Импорт и переключение frontend с передачей version/key/fingerprint и чтением страниц экспорта — B-09/B-10. Финальный шаг Java-команды уже перечитывает status/version/роль из БД; это не объявляет ещё не перенесённый Telegram transport готовым.

## Общая задача для факультетов и legacy create

`facultyId="all"` означает одну shared-задачу для явно назначенных активных участников разных активных факультетов. V010 хранит `faculty_all=true`, `faculty_id=null`, не создавая фиктивный факультет и не смешивая задачу с core. Обычная core-задача имеет `faculty_all=false` и null faculty_id. Контур неизменяем при правке. Допустимы только faculty_responsible/faculty_helper с membership; core и участники неактивного факультета не назначаются. Faculty видит all-задачу только при собственном назначении и membership, независимо от общего охвата; адресные заметки коллег остаются скрыты. Общий статус и completedBy сохраняют shared-семантику. Список/совместимый DTO/история/outbox возвращают `facultyId=all`; CSV подписывает его «Все факультеты». На чтении область all не расширяет аудиторию уведомлений: она определяется assignments.

Java `POST /api/task/create` и `POST /api/faculty/task/create` принимают старые поля `assignedTo` (ID или список IDs), `competency/competencies` (имена существующих активных компетенций своего scope), `deadline`, `tips`, `reminders`, `eventId`, `priority`. Дедлайн обязателен и строго календарный; faculty route дополнительно требует facultyId и хотя бы одного исполнителя. Core route не принимает facultyId. При отсутствии priority используется normal. Создавать могут только admin/organizer с сессией и same-origin Origin; requesterId/creatorId из тела не являются источником личности и игнорируются. Ответ 200 `{success:true,task:<совместимый DTO>}`. Idempotency-Key обязателен; повтор возвращает сохранённый ответ без второго task/history/outbox/reminder. Пространства legacy/core/faculty create отделены, но ключ всегда scoped по actor.

Draft IDs напоминаний при create заменяются серверными IDs; никакие клиентские sent/anchor-маркеры не записываются. Core начинает open/assigned по назначениям; legacy faculty сохраняет прежний старт waiting. V1 create продолжает open/assigned. Все изменения проходят через общий TaskService и пишутся в одной транзакции с audit/outbox. Java routes готовы для будущего переключения; текущий frontend/Node production ещё не перенаправлен на Java.

## Legacy update/comment/status

Java принимает `POST /api/task/update`, `/api/faculty/task/update`, `/api/task/comment`, `/api/task/status`. Для всех обязательны сессия, same-origin Origin, Idempotency-Key, taskId и целочисленный `version>=0`. Нулевую версию не заменяем на 1; отсутствие, отрицательное, строковое, дробное или переполненное значение отклоняется с 400. RequesterId/userId не дают полномочий: actor берётся только из сессии. Ответ 200 `{success:true,task:<совместимый DTO>}`, точный повтор replay без новых записей. Тот же ключ с другим телом — 409. Это подготовленные Java-маршруты; часть текущих frontend mutations ещё не передаёт version/key, поэтому переключение требует отдельной правки B-09/B-10, без небезопасного server-side подбора текущей версии.

Update — частичная правка в общей транзакции. Поля, которых нет в JSON, сохраняются; description/sow/eventId можно очистить null. Deadline при явной передаче должен быть реальной датой YYYY-MM-DD. AssignedTo=null/[] снимает назначения; competencies=null/[] очищает ссылки, competency — совместимый одиночный вариант. Tips/reminders: отсутствие/null сохраняет, [] очищает; неизменные напоминания сохраняют IDs/anchor/sent/nextDue, даже при правке только title. Новые reminder draft_ IDs заменяются серверными; чужие server-issued IDs не принимаются. Контур core/faculty/all неизменяем; неверный legacy route получает 400. Выполненную/отменённую задачу редактировать нельзя, закрытые комментарии не перезаписываются. Созданный доменный Mutation проходит bean validation, правила и версионную проверку TaskService.

Comment переводит assigneeId в targetAssigneeId для coordinator (цель обязательна); executor всегда пишет от своего имени и для себя, даже при подменённых requesterId/assigneeId. Текст до 4000 символов не обрезается молча. Заметки append-only, target проверяется по актуальным назначениям, faculty получает только собственные заметки. Status переводит version, status, целые timeSpentMinutes 1..60000 и completionComment в общую команду. Закрытые результаты сохраняются; попытка изменить минуты/текст повторным completed получает completion_reopen_required/409, а не ложное сообщение об успешной правке. Сначала требуется явное переоткрытие. Реальный completedBy — session actor, не requesterId из тела.

## Legacy claim/release/delete

Java принимает `POST /api/task/claim`, `/api/task/release`, `/api/task/delete`. Обязательны session, Origin, Idempotency-Key и `{taskId,version}`. UserId/requesterId в теле не выбирают исполнителя или автора: actor только из сессии. Ответ `{success:true,task}`; release дополнительно возвращает becameOpen и remainingAssigneeIds. Точный повтор с тем же ключом возвращает сохранённый ответ без новых history/audit/outbox; новый ключ не подменяет версионную проверку.

Claim берёт только свободную core-задачу, проверяет компетенции и атомарно назначает session actor. Конкурентные претенденты не могут оба выиграть. Release снимает только собственное назначение и сохраняет коллег; после последнего исполнителя задача возвращается в open. Повтор release с новым ключом от уже неназначенного пользователя получает 403; для безопасного повтора нужно сохранить исходный ключ. Delete означает отмену, не физическое удаление: автор/admin сохраняет cancelledBy, историю, выключает будущие напоминания и фиксирует outbox в общей транзакции. Отменённая задача не может снова быть взята или освобождена.

## Ручное напоминание

`POST /api/task/notify` требует session, Origin, Idempotency-Key и `{taskId,version}`. Автор/admin проверяется по сессии; задачи без назначений, без активных зарегистрированных адресатов, cancelled/removed и stale version отвергаются. Completed допускается, как в старом API. Снимок задания и активных адресатов (userId/telegramId) сохраняется в `task.manual_reminder` outbox вместе с audit/idempotency в одной транзакции. Адресные комментарии не входят в общий payload. Все задания тихие (`disableNotification=true`).

Ответ `{success,outboxId,queued,delivered:0,unavailable,deliveryStatus:"pending"}`: queued — число активных адресатов с Telegram ID, unavailable — без него. Это сохранённое намерение, не подтверждённая отправка и не обещание доставки ровно в момент запроса. Task version/history не меняются. Повтор с тем же ключом не создаёт второе задание; другой ключ — новое явное напоминание. Ошибка outbox откатывает audit и idempotency. Maintenance отменяет pending задания; worker B-07 проверяет task version/removed/cancelled, права координатора и актуальный доступ адресата перед HTTP. Материализация и сроки: [manual-task-delivery.md](manual-task-delivery.md). Production frontend ещё не переключён.

## Очистка архива, сброс сезона и восстановление

Все маршруты ниже доступны только admin. Предварительный просмотр — `GET /api/v1/tasks/archive/preview` (только completed/cancelled) или `GET /api/v1/tasks/season-reset/preview` (все видимые задачи). Ответ содержит count, statusCounts, точный состав tasks `{id,version,status}` и SHA-256 fingerprint. `POST /api/v1/tasks/archive/clear` принимает `{fingerprint}`, `POST /api/v1/tasks/season-reset` — `{fingerprint,confirmation:"СБРОСИТЬ СЕЗОН"}`. Обе команды требуют Idempotency-Key. Изменение версии/состава/статуса после preview вызывает 409 без очистки. Пустая выборка — no-op без создания recovery record.

V009 добавляет task_recovery_operations и soft removal. В одной транзакции сохраняется JSONB-копия выбранных tasks вместе с assignments, competencies, tips, comments, reminders и history, затем задачи скрываются, task/reminder versions повышаются, расписания приостанавливаются. Физического удаления нет: log/export сохраняют прежнюю историю, frontend/list/get/faculty исключают скрытые задачи, старые кнопки получают 404. Незавершённые задачи не входят в очистку архива. Pending/retry/processing task outbox отменяется, чтобы накопленные уведомления не пришли после reset; уже отправленное сообщение этим не отзывается.

Команды задач берут общий PostgreSQL advisory lock shared до row locks; bulk maintenance — тот же lock exclusive. Это не сериализует обычные create между собой, но исключает незаметное включение конкурентно созданной задачи в старый preview. Future worker B-07 также должен проверять removed_at, task/reminder version и outbox status/lease перед отправкой; сеть нельзя удерживать внутри транзакционного lock.

Ответ очистки содержит recoveryId. `GET /api/v1/tasks/recovery/{id}` отдаёт admin копию; `POST /api/v1/tasks/recovery/{id}/restore` с Idempotency-Key возвращает весь состав, если его removal operation и версии не изменились. Несоответствие — 409, восстановление целиком откатывается. Повтор восстановления — no-op. Versions не откатываются к старым значениям: старые команды остаются stale. Настройки и sent-маркеры сохраняются; рабочие repeat-конфигурации выбирают следующий будущий тик, выполненные/cancelled задачи и удалённые/отправленные once-reminders не возобновляются. Отменённый outbox не оживает. Завершение и комментарий результата сохраняются в совместимом DTO независимо от повышения версии при restore.

Recovery-копия находится в той же PostgreSQL и защищает от ошибочной очистки, но не от потери диска/всей БД; внешний backup/restore drill остаётся релизным требованием. Production очистка в этой работе не запускалась — только тестовые контейнеры.

Legacy admin routes: `POST /api/task/archive/preview`, `/api/task/archive/clear`, `/api/task/season-reset/preview`, `/api/task/season-reset`. Preview возвращает прежние success/taskIds/count/completedCount/cancelledCount или statusCounts и добавляет fingerprint/tasks с версиями. Clear/reset обязательно принимают fingerprint из preview и Idempotency-Key; taskIds опциональны, но при наличии должны точно совпадать (дубликаты тоже отклоняются). Отсутствие fingerprint — 400, изменение версии даже при тех же ID — 409. Нет автоматического получения свежего fingerprint вместо пользовательского подтверждения. Reset требует точную фразу. Ответ добавляет прежние removedCount/remainingCount/backupId/operationId, где backupId/operationId — recoveryId, не путь на сервере; пустая операция не создаёт фиктивной копии. Устаревший `/api/task/log/clear` для admin возвращает 410 и ничего не удаляет, остальным — 403. Actor всегда из сессии, requesterId игнорируется. Frontend должен использовать новый fingerprint при B-09/B-10.

`GET /api/task/export` остаётся отчётом текущих видимых задач (не журнала изменений). Admin-only UTF-8 BOM CSV `tasks.csv`, limit 1..100, cursor — ID последней задачи, продолжение в X-Next-Cursor. Есть прежние поля задания/описания/ТЗ/исполнителей/дедлайна/сроков/приоритета/подсказок и дополнительно ID/faculty/completedBy/version. Removed задачи исключены. Времена московские, ячейки защищены от формул, кавычки/переносы экранированы, no-store/nosniff. Старый HTML под видом XLS намеренно не воспроизводится; frontend должен читать CSV и все страницы. `/api/v1/tasks/export` отдельно сохраняет исторический CSV, включая cleared задачи. Обе выборки ограничены страницами и не являются атомарным backup всего сезона.

## Журнал и экспорт

`GET /api/v1/tasks/log` доступен admin/organizer; faculty не получает общий журнал и адресные заметки коллег. Источник — append-only `task_status_history`, а не текущая строка tasks и не отдельная копия task_log. Запись возвращает taskId, actorId/actorName, прежний/новый статус, occurredAt и сохранённые details. CompletedBy берётся из snapshot конкретного изменения: переоткрытие не переписывает прежнее завершение. Новые snapshots сохраняют автора/время создания, время завершения/отмены и комментарии именно этого изменения. Старые отсутствующие поля не достраиваются по текущей задаче. Имена людей/мероприятия/факультета — текущие подписи к историческим IDs, не исторические версии имён.

Пагинация: `limit=1..100` (default 50), cursor — ID последней записи, порядок `(occurred_at,id)`. Envelope `{items,nextCursor}`; null означает последнюю страницу. Неизвестный cursor — 400. V008 добавляет индекс глобального журнала. Каждая страница читается в одном repeatable-read snapshot. Между запросами snapshot не удерживается: это живой журнал, не атомарный backup всего сезона; поздний commit с более ранним occurredAt может потребовать нового прохода. Recovery при очистке — отдельная транзакционная операция V009.

`GET /api/v1/tasks/export` только для admin, те же cursor/limit (default 100). Возвращает страницу того же журнала в настоящем `.csv`: UTF-8 BOM, разделитель `;`, CRLF, полный заголовок на каждой странице, статусы/действия по-русски, время в Europe/Moscow. `X-Next-Cursor` присутствует только при наличии следующей страницы. При сборке файла клиент оставляет BOM/заголовок первой страницы и добавляет только строки данных остальных; нужен CSV parser, не split по переводу строки, поскольку тексты могут быть многострочными. Кавычки/разделители экранируются; `=,+,-,@` после пробельных/невидимых префиксов нейтрализуются апострофом против spreadsheet formula injection. Raw JSON сохраняет исходный текст. Export не мутирует tasks/history/outbox. Legacy `/api/task/export` и кнопка фронтенда пока не переключены на Java.

## Подсказки, напоминания и совместимый DTO

Create/update принимает `tips` (до 50 строк по 1000 символов) и `reminders` (до трёх конфигураций). `null` или отсутствие этих полей при правке сохраняет данные, `[]` явно очищает. Подсказки сохраняют порядок. Тексты комментариев и время назначения оставшихся исполнителей не удаляются при правке деталей.

Напоминание задаётся `type=before_deadline|repeat`, положительным целым `value`, `unit=days|hours` и необязательным существующим server-issued `id`. Новые IDs выдаёт сервер; чужой/удалённый ID отклоняется. При отсутствии ID неизменная конфигурация сопоставляется с существующей, поэтому повторная правка не обнуляет sent-маркеры и не создаёт дубль. До дедлайна требуется `due_at`; повторное напоминание допускается без дедлайна. Поля `sent_at`, `last_sent_at`, `anchor_at`, `next_due_at`, `version` меняет сервер.

`anchor_at` фиксирует исходное расписание. Повторные тики вычисляются от anchor, а после переоткрытия выбирается следующий будущий тик, без накопления дрейфа. Завершение/отмена приостанавливают scheduling, сохраняя настройки. Удаление выставляет `enabled=false` и повышает reminder version; запись и sent-маркеры сохраняются для дедупликации. Переоткрытие не возобновляет удалённое напоминание и не повторяет уже отправленное одноразовое. Изменение типа/интервала или даты одноразового напоминания создаёт новую reminder version и сбрасывает её sent-маркеры. Worker B-07 должен проверять enabled/active/version и состояние задачи перед отправкой. Создание occurrence и фактическая отправка пока относятся к B-07.

Миграция V007 добавляет enabled-конфигурацию и различает discussion/completion в комментариях. Task version привязывает комментарий к конкретному завершению; старые результаты остаются в истории. Java `/api/state` уже возвращает реальные задачи со старой формой `assignedTo`, `deadline`, `competencies`, `tips`, `reminders`, `assigneeNotes`, `completionComments`. `/api/faculty/my-tasks` возвращает тот же безопасный DTO в envelope с serverNow/timeZone, только для своего faculty scope и назначения. Общий `/api/state` остаётся закрытым для faculty. Чтение DTO использует один repeatable-read snapshot, чтобы статус и назначения не разъезжались при конкурентной правке.
