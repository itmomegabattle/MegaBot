# Антиспам создания и правок рассылок: B-07

Оба маршрута POST /api/v1/broadcasts и POST /api/team/broadcast вызывают один BroadcastService; общий BroadcastCreationQuota резервирует лимиты в той же транзакции, что broadcast/targets/deliveries/audit/idempotency. PATCH также резервирует новый запрос и объём полной новой ревизии: нельзя создать малую аудиторию и расширить её в обход лимита.

На действующего session actor, включая admin: по умолчанию 10 принятых команд за 10 минут и 500 физических сообщений за час. После V029 объём равен sendable targets × число частей; одночастная рассылка сохраняет прежний расход. Недоступный Telegram не расходует объём, но создание всё равно расходует запрос. Отмена не возвращает лимит, ручной повтор существующей части не создаёт новую аудиторию (транспортная quota продолжает действовать). Имя настройки BROADCAST_VOLUME_MAX_RECIPIENTS сохранено для совместимости. Эти лимиты не заменяют Telegram bot/chat транспортную quota.

V023 хранит одну строку на автора с двумя независимыми fixed windows; PostgreSQL row lock сериализует конкурентные команды между API и процессами. После lock используется clock_timestamp БД, не JVM/браузер. Перезапуск приложения и новая сессия не очищают строки. Каждое окно начинается с первой принятой команды и сбрасывается при истечении своего срока. Это сохранённая Node fixed-window семантика, не sliding window: на границе окон допустим соседний burst, ограниченный транспортной quota.

Idempotency replay возвращается до domain command и повторно лимиты не резервирует. Изменённый запрос с тем же ключом — 409, не новая команда. Невалидная аудитория/расписание и неудачная materialization откатывают также счётчики. Исчерпанный запрос/объём — 429 broadcast_creation_rate_limited, без частичного broadcast или изменения прежней ревизии. В отличие от старого in-memory Node лимиты сохраняются после рестарта; два ограничения резервируются атомарно, отказ объёма не сжигает запрос.

Настройки окружения прежние: BROADCAST_RATE_LIMIT_WINDOW_MS=600000, BROADCAST_RATE_LIMIT_MAX=10, BROADCAST_VOLUME_WINDOW_MS=3600000, BROADCAST_VOLUME_MAX_RECIPIENTS=500. Все значения положительные; окна максимум год, request max 1 млн, volume max 1 млрд. Неверная конфигурация останавливает startup, а не отключает защиту. Увеличение конфигурации не обнуляет историю текущего окна.

Ponytail: row lock и CHECK PostgreSQL вместо Redis/in-memory limiter/фонового cleanup; общая точка BroadcastService вместо копий в контроллерах. Новых зависимостей нет. Одна строка на существующего пользователя; при удалении пользователя FK очищает её, деактивация не сбрасывает лимит. Production sender остаётся выключен, реальные сообщения не отправлялись. B-07 не закрыт: другие occurrences/group allowlist/UI/exploitation и live SLO остаются.
