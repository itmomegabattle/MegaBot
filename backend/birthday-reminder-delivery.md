# Birthday occurrences · B-07

Три самостоятельных намерения: за 2 дня, за день и в день рождения. Дата — календарная `LocalDate` в `Europe/Moscow`, без UTC-полуночи и без зависимости от зоны ОС. Владелец 05.10.2026 подтвердил **12:00 МСК** для всех трёх напоминаний: `BIRTHDAY_REMINDER_HOUR=12` — новый default Java/Node/Compose и пример настройки. Закрытие сбора остаётся в 19:00. Sender выключен по умолчанию, production не переключён; уже заданное override=10 не меняется само и должно быть обновлено при согласованном релизе. Существующие сохранённые occurrences не переписываются и не порождают повторных уведомлений.

V026 сохраняет unique `(birthday_user_id,birthday_date,days_before)`, immutable targets и delivery links атомарно. Материализация вызывается существующим worker, отдельного scheduler/очереди/зависимостей нет. Один снимок команды используется для всех сегодняшних birthday occurrences; для значительно большей команды нужны сохранённые снимки и поэтапная материализация, а не расширение аудитории во время отправки.

Источник времени — PostgreSQL `clock_timestamp()`. До установленного часа новые occurrences не создаются; после него восстанавливается только текущая московская дата, expiry — полночь следующего дня. Это сохраняет прежнюю дневную recovery-семантику birthday, **не** 15-minute grace разовой рассылки. Пропущенные дни не проигрываются, существующие deliveries закрывает общий expiry. Dedupe/429/quota/token/lease/retry/unknown — общие. Отступление часов после claim блокирует ранний start, но не отменяет намерение; interrupted HTTP становится unknown без автоматического перевыпуска.

Именинник и адресаты — активные зарегистрированные admin/organizer. Faculty не получает данные core-команды и не является источником её birthday-рассылки. Сам именинник исключён при снимке и повторно в gate. Missing Telegram сохраняется unavailable; новые участники и новые привязки текущий snapshot не расширяют. Перед start перепроверяются source role/active/registered/день-месяц рождения, recipient permissions, неизменный положительный личный chat ID и отсутствие topic. Удаление/перенос даты рождения блокирует старое намерение. При смене даты может появиться новый самостоятельный occurrence, а sent/unknown старого не rearm-ится.

Возраст и год рождения **не выбираются SQL-запросом и не публикуются**: согласно SEC-05 коллегам доступны день и месяц, даже если прежний Node-текст содержал возраст. В остальном текст/сумма/платёжные настройки сохранены. `BIRTHDAY_PAYMENT_PHONE`, `BIRTHDAY_PAYMENT_BANK`, `BIRTHDAY_GIFT_MAX_AMOUNT` задают реквизиты и максимальную целую сумму в рублях (по умолчанию прежние значения, 400). Эти значения фиксируются в двух вариантах текста при создании occurrence; изменение конфигурации не переписывает старые сообщения.

Дедлайн сбора — **19:00 МСК дня рождения**. У сохранённой delivery есть открытый и закрытый текст. Сразу перед HTTP после quota/start/heartbeat очередь выбирает вариант по текущим часам БД, а не по времени материализации. Поэтому queued/retry сообщение, созданное до 19:00, после границы говорит «сбор завершён» и не содержит реквизиты/просьбу перевести деньги. Дополнительный запрос выполняется только для birthday deliveries; другие категории не затронуты. Невалидный закрытый вариант прекращается без HTTP, не превращается в ложный unknown. Проверка не обещает отозвать сообщение, внешний запрос которого уже начался до границы.

29 февраля сохраняет прежнюю календарную политику: occurrence есть только в високосный год (27/28/29 февраля), автоматического переноса на 28 февраля в обычный год нет. Новая политика требует решения владельца, не скрытой миграции.

Бот получает обычный текст, `disable_notification=false`; финальное Markdown-оформление остаётся последним CHAT-01. UI/ручной retry системных occurrences и эксплуатационная приёмка TIME-07 остаются впереди. Тесты подменяют SQL clock только в своей Testcontainers PostgreSQL, восстанавливают его после каждого сценария и используют fake transport, без сообщений live-test/production.

## Приёмка

Исторический прогон до изменения часа: полный `verify` — **322 tests, 0 failures/errors/skipped, BUILD SUCCESS**, log `target/birthday-reminder-final-verify.log`. Он проверял прежние 10:00. После решения владельца suite использует default из application.yml без явного override часа: проверяет отсутствие materialization в 10:00 и 11:59:59.999 МСК, создание ровно в 12:00 для каждого из трёх дней, intended_at=09:00Z, clock-back/recovery и прежние независимые offsets/expiry, snapshot/access/rollback/two workers, закрытие сбора в 19:00, 429/unknown, смену года и leap policy. Эти fake-тесты не подтверждают production SLO или доставку на устройство.

Новый полный verify 05.10.2026: **370 tests, 0 failures/errors/skipped, BUILD SUCCESS**, включая все **14** birthday scenarios; log `target/process-crash-birthday-final-verify.log`. Node `verify:birthdays`, lint/build и `docker compose config --quiet` также прошли. Изменены только исходники/defaults/шаблоны и документация; production/live-test runtime, actual env и существующие occurrences не менялись.
