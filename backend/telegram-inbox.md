# Telegram inbox — B-08, локальный приём

`TelegramInbox.accept(botId, payloadBytes)` — внутренний сервис. Добавлены отдельный выключенный по умолчанию `POST /api/v1/telegram/webhook`, lifecycle `TelegramInboxQueue` и ручной/local `TelegramCommandWorker` с общим handler для личных `/start`, помощи, профиля и роль-зависимого меню; ответы сохраняются в outbox. `TelegramReplyPlanner` подключает их к существующей очереди/sender; sender остаётся выключенным. Нет автоматического incoming consumer, polling или callback mutations. Production/test-bot настройки не меняются. Это локальные подблоки B-08, не законченная Telegram-интеграция.

## Граница приёма

Используется существующая `telegram_inbox` из V004, без миграций, broker и новых зависимостей. Bot ID поступает из доверенной конфигурации транспорта, не из JSON и не из URL пользователя. Bot token передавать в сервис нельзя. Webhook проверяет secret **до** вызова сервиса/чтения body; будущий polling обязан дождаться сохранения всех updates перед продвижением offset. Webhook и polling одновременно включать нельзя. Эти правила подтверждены [Telegram Bot API](https://core.telegram.org/bots/api#getting-updates); никакие `setWebhook`/`deleteWebhook`/`getUpdates` не вызываются.

- Payload ограничен 1 MiB до JSON parsing; пустой, malformed, trailing JSON и некорректный `update_id` отвергаются. Размер — внутренний защитный предел, не заявленный лимит Telegram. HTTP-транспорт ограничивает чтение body до1MiB+1 вместо неограниченного выделения памяти и отвечает безопасно при ошибках.
- `update_id` — неотрицательный целый bigint, не строка/дробь/overflow. Валидация envelope не заменяет проверки полей и прав внутри будущих команд.
- Технический ID записи — стандартный UUID с префиксом `inbox_`. Он не является dedupe key: unique `(bot_id, update_id)` и `ON CONFLICT (bot_id, update_id) DO NOTHING` дают одну запись при конкурентных повторах. Детерминированный primary key не используется: отдельные unique indexes могут конфликтовать при конкурентных inserts раньше выбранного conflict target. Повтор означает «уже сохранено», **не «уже обработано»**; первое payload, attempts, lease и completed status не переписываются. Разные боты не смешиваются.
- `REQUIRES_NEW`, timeout5s создаёт отдельную короткую транзакцию. Вызов через Spring bean возвращается только после COMMIT; ошибка записи/COMMIT приводит к отсутствию положительного ack. Timeout транзакции не заменяет ограничения ожидания соединения/сетевого чтения — их задают pool/server/proxy. Обратный откат вызывающей транзакции не стирает уже принятую запись. Не вызывать метод через self-invocation вне Spring proxy.
- Payload сохраняется целиком как jsonb: callback ID/data, thread ID и неизвестные типы не отбрасываются. Неизвестные поля сохраняются, но не исполняются этим сервисом.
- `chat_key` включает bot ID. Chat находится в update.chat либо callback.message.chat; если chat отсутствует, используется положительный from.id (`user`), иначе `unscoped`. Topic остаётся в payload; ключ объединяет темы одного чата для будущей последовательной обработки. Ключ — группировка, не проверка полномочий/группового allowlist и не реализованный алгоритм ordering. Полнота маршрутизации остальных Telegram типов проверяется при реализации их обработчиков.
- Состояние новой записи `received`, attempts=0, timestamps по БД. Нет доменных изменений, ответов бота или сброса существующих updates. При некорректном JSON безопасная ошибка без исходного текста/parser exception. Ошибки БД распространяются внутри сервиса; HTTP-адаптер преобразует DataAccess/Transaction/IOException в safe503 без raw SQL/credentials.

## HTTP transport — disabled by default

Настройки в `backend/.env.example`: `MEGABOT_TELEGRAM_INCOMING_MODE=disabled`, `MEGABOT_TELEGRAM_BOT_ID=` и `MEGABOT_TELEGRAM_WEBHOOK_SECRET=`. Это отдельно от outgoing/fake `MEGABOT_TELEGRAM_MODE` и sender enabled. Только `disabled`/`webhook`; неподдерживаемый режим приводит к безопасной ошибке старта. Webhook требует числового bot ID и отдельного случайного secret длиной32…256 Telegram-safe символов. Значение secret не вставлять в команды/URL/logs; актуальный env и Compose не включались/не менялись.

Endpoint имеет собственную exact-path security chain: POST не требует session/cookie/Origin, но secret обязателен в единственном `X-Telegram-Bot-Api-Secret-Token` header; constant-time compare. Cookies не обходят secret и не вовлекают session DB до проверки. Остальной API остаётся в прежней session/origin цепочке. Другие HTTP методы запрещены, соседние пути не становятся публичными.

Для JSON POST: disabled→503; missing/wrong/repeated secret→401 до чтения body; malformed envelope/trailing JSON→400; size>1MiB→413 до parsing (Content-Length предварительно, bounded `readNBytes` также для chunked/unknown length); неправильный media type→415. Safe read/DB/commit failure→503. Новая или уже durable запись→200, пустое тело/no-store только после возврата транзакционного proxy. Это не означает выполнение команды. Reverse proxy/servlet должны дополнительно ограничивать скорость/время чтения тела и число соединений; in-process memory cap не является полной anti-DoS защитой. Дедуп callback IDs между разными updates, права доменных команд и обработчик всё ещё впереди.

## Личный `/start` — DB/outbox, без отправки

`TelegramCommandWorker.processOne(configuredBotId)` — только ручной/local проход, не HTTP endpoint и не scheduler. Требует отсутствие внешней транзакции; берёт одну lease, apply запускает общий private handler в короткой транзакции. Исключения обрабатываются после rollback: malformed private command→failed/invalid_private_command (прежний внутренний код invalid_start переименован); неподдержанные команды/группы/callbacks→retry/unsupported_command через1h; остальные failures→retry/command_processing_failed с задержкой5…300s по attempts. Если reject тоже не удалось или lease истекла, durable processing восстановится при следующем claim. Bool означает «запись осмотрена», не successful/provider delivered. Unsupported head блокирует следующие updates чата: **поэтому автоматический worker не включать, пока routing policy/handlers не готовы**. Лимита потери после8 попыток нет.

- Поддержан обычный `message` в private chat с `/start` или `/start <payload>` (payload не даёт прав и игнорируется). `/start@username`, регистрационные alias-кнопки, edited/business messages, группы и callback flows ещё не поддержаны. Для private start требуются positive integral 64-bit from/chat/message/date, chat ID=from ID, is_bot=false, first_name и bounded string identity fields; chat_key обязан соответствовать persisted chat. Forward/via_bot/sender_chat/business context не используется для регистрации. Malformed fields не создают ответ/привязку. Нельзя доставать identity из callback-data, произвольного верхнего user/role/admin поля или deep-link payload.
- Общий `TelegramIdentityService` теперь используется и Mini App login, и ботом. Это внутренний сервис, не новый способ публичной аутентификации: вызывающий обязан сначала проверить Mini App HMAC либо trusted inbox transport. Существующая привязка по numeric Telegram ID имеет приоритет; иначе ровно один активный непривязанный invite по case-insensitive username с/без@. Ambiguous/unknown/inactive→отказ. Bootstrap/admin — только настроенный numeric ADMIN_TELEGRAM_IDS, не username/payload. После candidate lookup managed profile refresh выполняется под PESSIMISTIC_WRITE; изменившаяся identity/активность/invite проверяется заново, конкурент не забирает уже привязанный профиль. Mini App auth сохраняет HTTP contract/status, но denial message теперь общий («не добавлен или недоступен»).
- Успешный start атомарно связывает numeric identity/registered, joined_at (не перезаписывается)/last_seen_at, private bot/chat binding и user history с response intent `telegram_command_reply` в существующем outbox. Core/admin/faculty получают свои welcome/menu payload; no Markdown parse_mode, CHAT-01 остаётся последним. Unknown/inactive/ambiguous получают только ограниченный отказ с «Помощь», без нового профиля/binding/history. `/start` не создаёт и не ротирует Mini App sessions, не удаляет входящие сообщения и не публикует в группу.
- Reply dedupe=`telegram:start:<botId>:<updateId>`; повтор того же update не создаёт ещё один welcome/history. Новое нажатие `/start` с новым update ID — отдельный ответ. Ответ содержит frozen bot/chat, optional recipientId/recipientRole, text, replyMarkup, sourceMessageId. Нет callback cross-update dedupe. **Pending outbox не означает sent**: bot history записывается только при подтверждённом результате sender. Task/meeting planners фильтруют свои aggregate/event types и новый event не потребляют. Доставка описана ниже; фактические outgoing env не менялись.

## Lifecycle очереди — без автоматического потребителя

`TelegramInboxQueue` использует V004, JdbcClient/Spring transactions и PostgreSQL row locks; без новых таблиц, broker или зависимостей. Его никто не вызывает автоматически. Публичный HTTP endpoint для claim/apply/reject не создаётся.

- `claim(botId, limit, duration)` берёт до100 голов разных чатов только указанного настроенного бота, возвращает payload из БД, новый UUID lease token и номер попытки. Аренда1…300s; дробные положительные секунды округляются вверх. `received/retry` должны быть due; истёкший `processing` переарендуется непосредственно с новым token. Отдельного scan/recovery scheduler пока нет: восстановление происходит при следующем claim.
- Голова определяется `(received_at, update_id, id)` среди **видимых уже принятых незавершённых** записей чата. Delayed retry, занятая/заблокированная или ещё действующая processing-голова блокирует последующие записи даже при `SKIP LOCKED`; обработка других чатов работает параллельно. Completed/явно failed не блокируют. Поздний COMMIT intake с более ранним received_at не создаёт вторую processing-аренду: наличие любого processing блокирует новые строки чата, а recovery сначала завершает уже взятую строку. Короткие claim-транзакции сериализованы PostgreSQL advisory lock по bot ID; после получения lock новый SQL statement получает свежий snapshot. Это закрывает phantom race между claim и поздним intake без новых таблиц. Lock не удерживается во время apply; при измеренном недостатке claim throughput заменить на per-chat locks. Это сериализация persisted reception order, **не восстановление исходной хронологии Telegram**: задержанный update или ещё незакоммиченный intake не известен claim snapshot, автоматически переупорядочить уже применённые команды нельзя. До включения worker отдельно зафиксировать политику reordered/старых mutations; не объявлять эту часть завершённой. Одного глобального high-water update ID здесь нет.
- `apply(id, token, action)` блокирует текущую запись и повторно проверяет срок аренды после ожидания row lock. Callback получает только persisted envelope, должен проверять identity/permissions/command fields и выполнять **только** локальные DB mutations и durable enqueue ответов в той же REQUIRED-транзакции. Нельзя HTTP/provider, async или вложенные `REQUIRES_NEW`: они нарушат атомарность. В конце повторная ownership/expiry проверка; completed, processed_at и изменения callback фиксируются вместе. Любая ошибка action, completion SQL или commit откатывает всё. Stale/expired/completed token не вызывает action; конкурентное применение одного update выполняет committed effects один раз. Это не dedupe разных update IDs с одинаковым callback ID.
- `reject(id, token, safeCode, retryDelay)` выполняется отдельно **после** отката apply. Retry1s…24h сохраняет голову и блокирует её последователей; null delay — явный terminal failed. Строка блокируется до последней проверки срока аренды: нельзя записать старую ошибку после ожидания lock/переаренды. Safe code — только `[a-z0-9_]{1,64}`, без exception messages/payload/secrets. Лимита «8 попыток, затем потерять команду» нет. Классификация permanent/transient, backoff и admin диагностика будут в command worker; failed не означает успешно выполнено.
- Все операции `REQUIRES_NEW`, timeout5s; вызывать через Spring proxy. Claim явно требует `READ_COMMITTED` для свежего snapshot после advisory lock, независимо от isolation внешней транзакции. DB-clock используется для due/lease/complete, а не часы JVM. Timeout не заменяет pool/сетевые ограничения. Если JVM исчезнет после claim, новая попытка возможна после expiry; если исчезнет во время apply до commit, DB откатит локальные изменения. Если commit состоялся, completed исключает повтор. Реальное аварийное завершение процесса inbox ещё не проверялось; тесты истёкших leases/rollback не выдаются за crash drill. Производительность head lookup/retention и recovery alarm проверяются отдельно перед release.
