Предлагаемая тема: **информационная система координации организаторов мероприятий

## 2. Предметная область

Команда организует мероприятия, подготовительные собрания, монтажи и неформальные
встречи. Участники обладают компетенциями и разной доступностью по дням и часам.
Для мероприятия создаются задачи, назначаются исполнители, фиксируются дедлайны,
статусы, комментарии и результаты. Часть поручений относится к факультетам:
для них действуют собственные участники, ответственные и границы доступа.

Администратор ведёт состав команды и справочники. Организатор отмечает доступность,
создаёт мероприятия и встречи, выполняет задачи. Факультетский ответственный
и помощник работают с разрешёнными факультетскими задачами; они не должны получать
данные основной команды или других факультетов только из-за знания ID объекта.
Telegram служит дополнительным каналом входа, ответов и уведомлений, а веб-интерфейс
предоставляет сводное представление данных и формы управления.

Без единой системы договорённости распределены по личным сообщениям и таблицам:
трудно найти актуальное назначение, согласовать время и понять, кто подтвердил
участие. Повторная отправка или устаревшая кнопка могут привести к ошибочным
действиям. Система должна хранить согласованное состояние и историю изменений.

## 3. Цели и решаемые задачи

1. Вести единый реестр пользователей, факультетов, компетенций и мероприятий.
2. Собирать доступность и организовывать встречи с явной аудиторией и RSVP.
3. Распределять задачи и отслеживать выполнение без утраты истории.
4. Изолировать факультетские данные и проверять права на сервере.
5. Планировать напоминания и контролировать результаты внешних отправок.
6. Обеспечить восстановление после ошибок, аудит и воспроизводимое развёртывание.

Новая самостоятельная регистрация и дальнейшее развитие факультетского раздела
входят в ближайшие продуктовые цели, но их подробные правила ещё не утверждены.
Нельзя считать существующий вход через Telegram готовой реализацией нового
процесса регистрации или автоматически выдавать новому пользователю роль.

## 4. Требования к целевой системе

### Функциональные требования

| ID | Требование |
| --- | --- |
| FR-01 | Идентифицировать пользователя, создавать и отзывать серверную сессию; проверять роль и принадлежность к факультету. |
| FR-02 | Администратору управлять пользователями, активностью, факультетами и компетенциями. |
| FR-03 | Сохранять доступность на конкретную календарную неделю, включая полную недоступность; обнаруживать конфликт версий. |
| FR-04 | Создавать мероприятия и встречи с датой, временем, длительностью и аудиторией; поддерживать изменение и отмену. |
| FR-05 | Фиксировать ответы участников на приглашения; не предоставлять RSVP постороннему пользователю. |
| FR-06 | Создавать задачи, назначать исполнителей и компетенции, менять статусы, хранить комментарии и историю. |
| FR-07 | Факультетским пользователям показывать только разрешённые задачи и доступные действия; доступ проверять до пагинации. |
| FR-08 | Планировать уведомления и рассылки, хранить попытки и результаты доставки, не повторять уже подтверждённую отправку автоматически. |
| FR-09 | Хранить аудит важных действий и предоставлять безопасную диагностику администратору. |
| FR-10 | Переносить legacy-данные только через проверку, staging и сверку; исторический импорт не должен создавать новые отправки. |

FR-08 и FR-10 описывают целевую систему, а не утверждение о полном production-паритете.

### Нефункциональные требования

- **Целостность:** изменение домена и запись события outbox выполняются одной
  транзакцией; PK/FK/UNIQUE/CHECK защищают данные в PostgreSQL.
- **Конкурентность:** команды используют версии и необходимые блокировки;
  устаревшее подтверждение не должно отменять более новое изменение.
- **Безопасность:** серверная авторизация каждого действия, ограниченный DTO,
  проверка Origin для cookie-запросов, валидация Telegram-подписи и webhook secret,
  отсутствие секретов в Git и диагностике.
- **Надёжность интеграций:** внешние HTTP-вызовы выполняются после фиксации домена;
  ограниченные повторные попытки, учёт rate limit и неопределённого результата.
  Абсолютная exactly-once доставка Telegram при сетевой неопределённости
  не обещается: неизвестный результат учитывается отдельно.
- **Время:** хранить моменты как `timestamptz`/`Instant`, календарные недели как даты;
  пользовательская зона — Europe/Moscow. Измерять задержку scheduler отдельно
  от времени доставки внешним сервисом; нулевая задержка не гарантируется.
- **Эксплуатация:** health/readiness, ограниченные логи без личных payload,
  корректное завершение процесса и проверяемые резервные копии.
- **Переносимость:** учебный Java-процесс должен запускаться без обязательного
  Docker; конкретные JDK, PostgreSQL, порт и квоты helios проверяются отдельно.
- **Проверяемость:** модульные, HTTP, интеграционные и конкурентные тесты;
  Testcontainers применяется локально/в CI, не является условием запуска на helios.

## 5. Акторы и основные прецеденты

Модель прецедентов для согласования:

| Актор | Основные прецеденты |
| --- | --- |
| Администратор | Войти; вести пользователей/справочники; управлять мероприятиями, встречами и задачами; просматривать диагностику. |
| Организатор | Войти; отметить доступность; назначить встречу; ответить на приглашение; создать/выполнить задачу. |
| Факультетский ответственный / помощник | Войти; посмотреть свои разрешённые факультетские задачи; изменить доступный статус. |
| Telegram | Передать подписанный вход/update; принять отправку; вернуть результат и provider message ID. |
| Планировщик | Выбрать наступившие задания; сформировать доставки; возобновить допустимые попытки после перезапуска. |

Факультетские роли имеют разные бизнес-полномочия; таблица не означает, что все
их действия идентичны. Точный процесс новой регистрации согласуется отдельно.

### UC-01. Отметить доступность

- Актор: организатор или администратор, прошедший авторизацию.
- Предусловие: выбрана календарная неделя и прочитана её версия.
- Основной сценарий: пользователь выбирает часы/недоступность → сервер проверяет
  права, даты и версию → изменяет только выбранную неделю → возвращает новую версию.
- Альтернативы: некорректный ввод отклоняется; при конфликте версии возвращается
  409, чужие и более новые изменения не затираются.
- Результат: недельная доступность сохранена, соседние недели неизменны.

### UC-02. Назначить встречу

- Актор: организатор или администратор.
- Предусловие: известны мероприятие при необходимости и разрешённая аудитория.
- Основной сценарий: задать вид, название, дату, время, длительность и участников →
  проверить данные → одной транзакцией сохранить встречу, снимок аудитории
  и outbox-событие → после commit подготовить приглашения.
- Альтернативы: неверные данные не сохраняются; повтор той же команды не создаёт
  вторую встречу; ошибка Telegram не отменяет уже сохранённую встречу.
- Результат: существует одна встреча с фиксируемыми ответами приглашённых.

### UC-03. Изменить статус факультетской задачи

- Актор: назначенный факультетский участник с действующими правами.
- Предусловие: задача доступна этому участнику, не удалена/закрыта, известна версия.
- Основной сценарий: выбрать задачу и допустимый статус → подтвердить → повторно
  проверить назначение, факультет, состояние и версию → атомарно сохранить статус,
  историю и событие уведомления.
- Альтернативы: смена назначения/версии/прав отменяет старое подтверждение;
  повтор не создаёт второго доменного эффекта; сбой транзакции откатывает весь шаг.
- Результат: статус и история согласованы. Telegram-диалог целиком ещё не завершён:
  в текущем снимке есть внутренний engine, но не законченная привязка к SENT-панели.

### UC-04. Ответить на приглашение

- Актор: пользователь из разрешённой аудитории встречи.
- Основной сценарий: открыть приглашение → выбрать ответ → проверить аудиторию
  и актуальность → сохранить ответ и обновить представление.
- Альтернативы: чужое/устаревшее приглашение не даёт прав; отменённая встреча
  не должна возобновляться от старой кнопки.
- Результат: один актуальный ответ пользователя, без подмены ответов других людей.

## 6. Архитектурное решение

Выбран **модульный монолит**: один Java-процесс и одна реляционная БД. Это позволяет
использовать общую транзакцию для критических команд и проще демонстрируется
на учебном сервере, чем набор микросервисов. Брокер сообщений и Kubernetes
не требуются: inbox/outbox и задания хранятся в PostgreSQL.

```text
Веб-клиент React                Telegram
       | HTTPS / REST              | updates / Bot API
       +---------------+-----------+
                       |
           Java / Spring MVC (один процесс)
           auth → controllers → domain services
                              → persistence
           inbox / outbox / scheduler / workers
                       |
                    JDBC / JPA
                       |
                   PostgreSQL
```

| Уровень / модуль | Ответственность и реализация |
| --- | --- |
| Представление | React/TypeScript: формы, списки, ошибки; не источник истины о правах. Будущее подключение Java API отдельно от текущего Node API. |
| HTTP и безопасность | Spring MVC, Jakarta Validation, Spring Security; вход, серверные сессии и ролевые проверки. |
| Домен | `team`, `events`, `availability`, `meetings`, `tasks`; общие правила для веб-команд и Telegram. |
| Хранение | PostgreSQL, JDBC/JdbcClient для транзакционных запросов и блокировок, JPA/Hibernate для используемых сущностей и проверки схемы. |
| Интеграции | `telegram`, `notifications`: persistent inbox/outbox, доставки, scheduler, интеграционные jobs; внешние вызовы вне доменной транзакции. |
| Поддержка | `common`, `compatibility`, `migration`: ошибки, аудит, legacy DTO и изолированный staging. |

Фактический стек снимка: Java 21, Spring Boot 4.1.1, Spring Web MVC,
Spring Security, Jakarta Validation, Spring Data JPA/Hibernate, JDBC,
PostgreSQL, Flyway, Maven Wrapper. Версии зависимостей задаёт `backend/pom.xml`.
Это предлагаемый преподавателю стек, а не подтверждённый выбор кафедры.

## 7. Организация данных

Главные сущности: пользователь, факультет, компетенция, мероприятие, встреча,
приглашённый участник/RSVP, календарная доступность, задача, назначение,
комментарий, напоминание и запись аудита.

Связи многие-ко-многим реализуются через отдельные таблицы: пользователь–компетенция,
задача–исполнитель, задача–компетенция, встреча–участник. Принадлежность пользователя
к факультету хранится отдельно от глобальной роли. Служебные таблицы сессий,
inbox/outbox, заданий и доставок не подменяют доменную модель.

В `backend/src/main/resources/db/migration/` находятся V001…V042 — 42 миграции
со схемой, индексами, ограничениями и служебными структурами. Flyway применяет
историю миграций; Hibernate использует `ddl-auto=validate`, а не автоматическую
перезапись схемы. Полную ER-модель и обязательные процедуры следующего этапа
нужно оформить и согласовать отдельно; существующие Java-запросы не означают,
что требования последующих этапов курсовой автоматически выполнены.

Реальные данные Node/Sheets не переносятся простым включением Java. Предусмотрен
отдельный путь: проверенный snapshot → неизменяемый оригинал → staging → сверка
и отказы → проверенный атомарный импорт. На дату снимка полный путь не завершён.

## 8. Развёртывание и демонстрация на helios

По [официальным требованиям курсовой ИС](https://se.ifmo.ru/courses/is/course-project)
демонстрация этапов должна учитывать helios. Техническая доступность окружения
именно для этой учётной записи ещё не проверена, доступа к серверу в этой задаче нет.

Предлагаемый учебный вариант:

1. Собрать исполняемый Spring Boot JAR локально или в CI с JDK 21.
2. Передать JAR по SSH в отдельный каталог учебного пользователя на helios.
3. Подключить выделенную учебную PostgreSQL/схему с минимальными правами;
   не использовать рабочую Google-таблицу, production-БД или реальные данные команды.
4. Запустить Java как пользовательский процесс на разрешённом непривилегированном
   порту. Docker, root, локальная установка PostgreSQL и Nginx не обязательны.
5. Демонстрировать REST API через разрешённый канал доступа/SSH-туннель;
   раздачу React и same-origin/CORS согласовать отдельно до демонстрации интерфейса.
6. Telegram/Google и отправки оставить выключенными; учебные данные синтетические.
   Реальные исходящие уведомления не нужны для защиты проектной архитектуры.

До запуска необходимо проверить JDK 21, версию/адрес PostgreSQL, разрешённый порт,
квоты памяти/диска, разрешённый способ фонового запуска и доступ через SSH.
Возможность использовать подходящий JDK и текущую схему надо подтвердить,
а не предполагать по результатам локального Docker-теста.

В [кафедральных материалах по PostgreSQL](https://se.ifmo.ru/courses/programming)
указаны учебные `pg`/`studs`; для своей учётной записи адрес, права и отдельную
схему нужно уточнить. Ни пароль, ни имя пользователя здесь не подставляются.
Использовать общую schema без изоляции опасно: Flyway и таблицы проекта должны
работать в согласованной выделенной schema. На helios это пока не настроено.

Параметры внешней конфигурации для профиля `prod`:

```text
SPRING_PROFILES_ACTIVE=prod
MEGABOT_DB_URL=jdbc:postgresql://<host>:<port>/<database>?currentSchema=<own_schema>
MEGABOT_DB_USERNAME=<учебный пользователь>
MEGABOT_DB_PASSWORD=<секрет вне Git>
SPRING_FLYWAY_DEFAULT_SCHEMA=<own_schema>
SPRING_FLYWAY_SCHEMAS=<own_schema>
SERVER_ADDRESS=127.0.0.1
SERVER_PORT=<разрешённый порт>
MEGABOT_TELEGRAM_INCOMING_MODE=disabled
MEGABOT_DELIVERY_ENABLED=false
MEGABOT_TELEGRAM_MODE=disabled
MEGABOT_GOOGLE_MODE=disabled
```

Это шаблон проектного развёртывания, не готовые учётные данные и не доказательство
успешного запуска. Секреты передаются окружением/защищённым конфигурационным файлом.
Без корректных credentials Telegram-вход нельзя объявлять настроенным; для
дальнейшей API-демонстрации потребуется отдельный безопасный учебный сценарий входа.
При локальной разработке Docker Compose/Testcontainers — удобный способ получить
изолированную БД, но они не входят в обязательную схему запуска на helios.

## 9. Что показывать на первом этапе и что осталось

На защите первого этапа: тема и границы системы, описание предметной области,
цели, таблица требований, акторы и UC-01…UC-04, выбор модульного монолита,
Java/PostgreSQL стек и план демонстрации на helios. Код и миграции — дополнительный
материал, не замена согласованию темы и отчёту.

Текущий снимок содержит Java API и доменные модули, схему V001…V042, локальные
тесты и checkpoint-документы в `backend/`. Незавершёнными остаются полный
legacy-перенос, Java frontend cutover, часть Telegram-диалогов (включая готовящийся
faculty status flow), эксплуатационная приёмка и реальный запуск на helios.

Перед сдачей требуется согласовать с преподавателем тему/прецеденты/стек,
добавить титульный лист и сведения об авторе по форме кафедры, при необходимости
