# Архитектура и данные

## Текущее положение

Приложение состоит из React Mini App, Express API, обработчика Telegram updates, Telegram long polling и JSON-хранилища. Такая схема подходит для раннего запуска, но ограничивает конкурентные операции, аудит и безопасную двустороннюю синхронизацию.

Фактический продакшен сейчас устроен как один Node-процесс на Selectel VDS:

`Telegram / браузер Mini App → megaorgiabot.ru → Caddy HTTPS → 127.0.0.1:3000 → Express server.ts → database.json`.

Telegram-сообщения не приходят через публичный webhook. Сервер сам забирает updates из Telegram Bot API long polling'ом, после чего прокидывает их во внутренний обработчик `/api/telegram-webhook`. При старте старый webhook удаляется, потому что Telegram не позволяет одновременно использовать webhook и long polling для одного бота.

## Целевая архитектурная граница

Логику следует постепенно разделить на домены:

- identity и права;
- availability;
- meetings;
- tasks и process templates;
- notifications;
- integrations;
- audit и archive.

Разделение не требует немедленного перехода на микросервисы. На ближайшем этапе достаточно модульного монолита с отдельными сервисами, репозиториями данных и тестируемыми правилами.

## Целевые сущности

### Организационные

- `User`;

- `Scope` — мероприятие, направление, блок или факультет;
- `Membership` — роль пользователя внутри области;
- `Event/Direction`;
- `Block`;

### Операционные

- `Task`, `TaskChecklistItem`, `TaskAssignment`, `TaskComment`;

### Исторические

- `AuditEvent`;
- `SyncCursor` и `SyncConflict`;
- `ArchivedTask` как состояние либо представление, а не обязательно отдельная таблица.

## База данных

Текущее хранилище — JSON-файл:

- локально: `database.json` в корне проекта;
- на сервере: `/opt/megabot/database.json`;
- путь можно переопределить переменной `DB_FILE`.

В этом файле хранятся пользователи, Telegram ID, роли, факультеты, компетенции, слоты доступности, встречи, задачи, факультетские задачи, сообщения бота, настройки и служебные данные напоминаний.

JSON-хранилище подходит для пилота и небольшой команды, если есть резервные копии и аккуратное обновление кода. Его слабые места: конкурентные записи, отсутствие миграций, сложный аудит, риск повредить файл ручным редактированием и невозможность нормальных транзакций.

Перед масштабным пилотом рекомендуется перейти с JSON на транзакционную БД, например PostgreSQL или SQLite как промежуточный шаг. Миграция должна включать:

1. явную схему и ограничения;
2. стабильные идентификаторы;
3. миграцию существующих данных;
4. резервную копию и проверку количества записей;
5. возможность временного отката;
6. тесты конкурентного взятия одной открытой задачи.

Критическая операция `claim task` должна быть атомарной: только один запрос может успешно занять одиночную задачу.

## Сетевое окружение

### Домен и DNS

Домен `megaorgiabot.ru` куплен и делегирован на DNS Selectel:

- `a.ns.selectel.ru`;
- `b.ns.selectel.ru`;
- `c.ns.selectel.ru`;
- `d.ns.selectel.ru`.

В DNS-зоне настроены A-записи:

- `megaorgiabot.ru → 139.100.235.189`;
- `www.megaorgiabot.ru → 139.100.235.189`.

После делегирования DNS может обновляться не мгновенно. Проверка выполняется командами:

```bash
dig megaorgiabot.ru +short
dig NS megaorgiabot.ru +short
curl -I https://megaorgiabot.ru
```

### HTTPS и reverse proxy

Caddy принимает публичные HTTP/HTTPS-запросы, автоматически получает TLS-сертификат Let's Encrypt и проксирует приложение:

```caddy
megaorgiabot.ru {
  reverse_proxy 127.0.0.1:3000
}

www.megaorgiabot.ru {
  redir https://megaorgiabot.ru{uri}
}
```

Node-приложение не должно напрямую слушать порт `443`: оно остаётся на внутреннем `3000`, а внешняя безопасность и сертификаты находятся на стороне Caddy.

### Процесс приложения

На сервере приложение лежит в `/opt/megabot` и запускается через PM2 процессом `megabot`. Сейчас используется команда `npm run dev`, то есть `tsx server.ts`. Это позволяет запускать TypeScript напрямую и быстро обновляться, но целевой production-вариант — запускать собранный сервер:

```bash
npm run build
pm2 start npm --name megabot -- run start
```

До смены команды PM2 важно отдельно проверить, что production-сборка корректно обслуживает Mini App, API и Telegram polling.

## Переменные окружения

Секреты не хранятся в репозитории. На сервере они лежат в `/opt/megabot/.env`.

Обязательные переменные:

- `TELEGRAM_BOT_TOKEN` — токен Telegram-бота;
- `WEBAPP_URL=https://megaorgiabot.ru` — публичный URL Mini App;
- `TELEGRAM_API_BASE=https://api.telegram.org` — адрес Telegram Bot API;
- `ADMIN_USERNAMES` — Telegram username администраторов;
- `ADMIN_TELEGRAM_IDS` — Telegram ID администраторов.

Опциональные переменные:

- `PORT` — порт Node-приложения, по умолчанию `3000`;
- `DB_FILE` — путь до JSON-БД;
- `DISABLE_TELEGRAM_POLLING=true` — отключает polling, полезно для локального запуска Mini App без конфликта с продакшен-ботом;
- `BIRTHDAY_PAYMENT_PHONE` и `BIRTHDAY_PAYMENT_BANK` — реквизиты для рассылки перед днями рождения;
- `HTTP_PROXY` или `HTTPS_PROXY` — прокси для Telegram Bot API, если сеть сервера требует обхода.

Telegram Bot API допускает только один активный long polling consumer. Если локальная машина и сервер одновременно запускают polling с одним токеном, один из процессов начнёт получать `409 Conflict`. Поэтому локальный запуск для фронтенда лучше делать с `DISABLE_TELEGRAM_POLLING=true`.

## Журнал событий

Для аналитики и аудита необходимо записывать минимум:

- создание и редактирование задачи;
- назначение, взятие, возврат и смену статуса;
- завершение, время и комментарий;
- создание, изменение и отмену собрания;
- приглашение, присоединение и RSVP;
- публикацию доступности;
- изменение ролей и областей доступа;
- отправку и результат уведомления;
- импорт, экспорт и конфликт синхронизации.

Событие содержит тип, время, инициатора, объект, область, предыдущие и новые значимые значения и correlation ID операции.

## Google Таблицы и Apps Script

### Рекомендуемый источник истины

База является главным источником операционных данных. Google Таблица — привычное представление и разрешённый канал редактирования только для явно выбранных полей.

### Порядок интеграции

1. Согласовать схему листов и идентификаторы строк.
2. Реализовать идемпотентный экспорт из базы.
3. Добавить подпись запросов, журналы и повтор неудачных операций.
4. Ввести `updatedAt` и версию записи.
5. Реализовать импорт из таблицы в тестовом режиме.
6. Добавить очередь конфликтов для ручного разрешения.
7. Только после наблюдения включить автоматическую двустороннюю синхронизацию.

### Конфликты

Нельзя молча использовать принцип «последняя запись победила» для важных изменений. Если обе стороны изменили запись после последней синхронизации, система создаёт конфликт и сохраняет обе версии до разрешения.

## Архивирование

- завершённая задача остаётся в БД и получает `archivedAt`;
- обычные экраны по умолчанию скрывают архив;
- Google Таблица может получать удобную архивную выгрузку;
- мягко удалённая запись хранит автора удаления, причину и время;
- физическая очистка выполняется только по утверждённой политике хранения и после резервного копирования.

## Производительность и наблюдаемость

Для каждого API-запроса нужны correlation ID и измерения этапов:

- получение запроса;
- проверка Telegram init data и прав;
- чтение данных;
- бизнес-операция;
- запись;
- отправка уведомлений;
- ответ клиенту.

Уведомления не должны удерживать пользовательский запрос дольше необходимого. Их следует отправлять через очередь или надёжный фоновой механизм с повтором и идемпотентностью.

В текущей реализации отправка уведомлений уже использует короткие таймауты, повтор отдельных Telegram-запросов и `Promise.allSettled` в массовых рассылках. Это снижает риск зависания одного пользовательского действия из-за одного недоступного получателя, но не заменяет полноценную очередь доставок и журнал попыток.

## Безопасность

- проверять Telegram `initData`, а не доверять переданному `userId`;
- авторизовывать каждую операцию на сервере;
- не хранить секреты в репозитории;
- не вставлять токен бота в документацию, историю коммитов и скриншоты;
- ограничить доступ к серверу, хранить root-пароль отдельно и по возможности перейти на SSH-ключи;
- регулярно копировать `/opt/megabot/database.json` перед обновлениями;
- ограничивать Apps Script подписанными запросами и минимальными правами;
- журналировать административные операции;
- минимизировать экспорт персональных данных;
- определить сроки хранения дат рождения, Telegram ID и истории активности.

## Тестовая стратегия

- unit-тесты доменных правил;
- API integration-тесты прав и конкурентных операций;
- миграционные проверки данных;
- end-to-end smoke для трёх основных процессов;
- контрактные тесты Google Apps Script;
- тесты идемпотентности webhook и уведомлений;
- ручная проверка на реальных Telegram-клиентах.

## Реализация чатового состояния и синхронизации — 2026-08-03

Файл `${DB_FILE}.chat-panels.json` имеет версионированную схему `version: 2` и хранит:

- текущий и известные message ID служебных панелей по chat ID;
- черновики слотов с `userId`, `weekStart` и набором часов;
- `pendingSheetExports` — пользователей, чьи изменения ещё надо отправить в Google Sheets.

Переходы внутри слотов используют `editMessageText`; новый message ID создаётся только при входе в сценарий. Callback проверяется против текущего ID. Сохранение сначала пишет `database.json`, затем очищает черновик и асинхронно выгружает доступность. Неудача оставляет user ID в очереди. Минутная сверка сначала очищает очередь экспорта, затем импортирует таблицу, чтобы старое внешнее значение не затёрло ожидающее локальное.

Ограничение файловой реализации: запись синхронная и нет межпроцессной транзакции. До горизонтального масштабирования следует перенести базу, чатовые состояния и очередь в PostgreSQL/Redis либо другое единое хранилище с блокировками и журналом событий.
