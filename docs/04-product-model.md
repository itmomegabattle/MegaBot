# Продуктовая модель и сценарии

## Иерархия работы

Целевая иерархия:

`Направление/мероприятие → блок → процесс/шаблон → задача → чек-лист → назначение → результат`.

Пользователь должен переключаться минимум между двумя представлениями:

- **Все задачи** — доступные ему задачи выбранного направления;
- **Мой блок** — задачи локальной области ответственности.

Дополнительно полезно представление «Мои задачи», но оно не заменяет фильтрацию по мероприятию и блоку.

## Роли и права

| Действие | Администратор | Ответственный | Организатор | Факультетская роль |
|---|---:|---:|---:|---:|
| Управлять всей командой | Да | Нет | Нет | Нет |
| Создавать направления и шаблоны | Да | В своём контуре по политике | Нет | Нет |
| Создавать и назначать задачи | Да | В своём контуре | Ограниченно | В факультетском контуре |
| Редактировать чужие задачи | Да | Созданные/локальные | Нет | По политике |
| Брать открытые задачи | Да | Да | Да | По политике |
| Назначать собрания | Да | В своём контуре | По политике | Нет по умолчанию |
| Смотреть персональные данные | По необходимости | Только свой контур | Только допустимые данные | Только свой контур |

Таблица задаёт направление. Перед реализацией права необходимо превратить в явную матрицу разрешений и покрыть тестами.

## Отмечаемость

### Целевой сценарий

1. Пользователь выбирает неделю.
2. Отмечает доступные часы по дням.
3. Видит прогресс заполнения и различает «черновик», «частично заполнено» и «отправлено».
4. Сохраняет или отправляет неделю.
5. Изменения синхронизируются с базой и, при подключении, с Google Таблицей.
6. Организатор встречи выбирает обязательных людей и получает подходящие окна.

### Требование, требующее решения

Текущий продукт трактует невыбранные слоты как недоступность и считает неделю отправленной после одного выбранного слота. Пожелание пользователя требует иной модели полноты. Возможные варианты:

- явная кнопка «Неделя заполнена»;
- статус заполнения каждого дня;
- обязательный ответ «нет доступности» для пустого дня;
- хранение черновика отдельно от опубликованного расписания.

До изменения схемы нужно выбрать один вариант и проверить его на команде.

## Собрания

### Типы

- **Общее** — вся команда или заранее определённая большая группа.
- **По теме/блоку** — участники конкретной компетенции, блока или процесса.
- **По людям** — явно выбранный состав.

Форма обязана показывать, кто будет приглашён, до сохранения собрания.

### Видимость и вступление

Целевая модель видимости:

- открытое — видно доступной аудитории, можно присоединиться;
- по запросу — видно, но вступление подтверждает организатор;
- закрытое — видно только приглашённым и администраторам.

### RSVP

Для каждого участника хранится отдельный ответ:

- приглашён, ответа нет;
- «я приду»;
- не приду;
- возможно;
- присоединился самостоятельно.

Кнопка «Я приду» должна менять состояние сразу, исключать повторные записи и показывать организатору актуальное число подтверждений.

## Задачи

### Обязательные поля

- название;
- описание или ТЗ;
- направление/мероприятие;
- блок или процесс;
- автор;
- статус;
- приоритет;
- дедлайн либо явное «без дедлайна»;
- модель назначения: открытая или назначенная.

### Дополнительные поля

- чек-лист;
- советы и вложения;
- один или несколько исполнителей;
- индивидуальный комментарий и статус каждого исполнителя;
- напоминания;
- оценка времени;
- фактическое время;
- итоговый комментарий;
- причина задержки;
- архивный статус и история изменений.

### Жизненный цикл

`Черновик → Открыта/Назначена → В работе → Ожидает → Выполнена → Архивирована`.

Возврат исполнителем переводит задачу в открытое состояние или требует переназначения — политика зависит от типа задачи. Удаление по умолчанию является мягким.

### Завершение

При завершении система спрашивает:

1. сколько времени потрачено;
2. что сделано;
3. были ли причины задержки или отклонения.

Для простых задач комментарий может быть необязательным. Для просроченных, критических или сильно отклонившихся от оценки задач он должен запрашиваться настойчивее.

### Исполнители

В карточке задачи каждый исполнитель раскрывается отдельно и показывает:

- индивидуальный статус;
- что делает сейчас;
- срок своей части;
- комментарий постановщика;
- комментарий исполнителя;
- последнее обновление.

### Уведомления

- при назначении;
- при существенном редактировании;
- по заданным интервалам до дедлайна;
- при просрочке;
- при смене статуса;
- по ручной кнопке «Уведомить всех исполнителей».

Повторные уведомления должны иметь защиту от дублей и журнал доставки.

## Шаблоны процессов мероприятий

Шаблон содержит граф задач, зависимости, относительные дедлайны, роли исполнителей и чек-листы. Создание экземпляра мероприятия копирует шаблон с конкретными датами и ответственными.

Шаблоны собираются с владельцами процессов, а не выводятся автоматически только из старых досок:

1. интервью и разбор фактического процесса;
2. фиксация графа и чек-листов;
3. ограниченный прогон;
4. исправление шаблона;
5. повторное использование.

## Контракт доступности — 2026-08-03

Черновик и сохранённая доступность — разные состояния. Toggle часа меняет только черновик; `Сохранить` атомарно переносит его в пользовательскую доступность текущей недели. После сохранения черновик удаляется. Если внешний экспорт не удался, сохранённые данные остаются действительными в приложении, а пользователь ставится в очередь повторной синхронизации.

Последнее подтверждённое изменение остаётся правилом разрешения конфликтов. Следующее улучшение модели — явная версия/время изменения на обеих сторонах и отображаемый пользователю статус конфликта или повторной отправки.

## Модель отмены дня слотов

При открытии дня черновик получает `dayBaseline = { dayIndex, hours }`. Toggle меняет только `slots`; повторный рендер не перезаписывает baseline. `Отменить` восстанавливает часы baseline и закрывает контекст дня, `К дням` принимает изменения в недельный черновик, `Сохранить` записывает всю неделю.

## Планируемая модель нескольких исполнителей

Сейчас `Task.status`, `completedAt` и `timeSpentMinutes` общие для всей задачи. Поэтому первый исполнитель, нажавший «Готово», завершает задачу у всех.

План без реализации в текущем релизе:

- `assignmentMode: shared | individual` обязателен при назначении нескольким людям;
- `shared` — один статус, завершить может любой назначенный, сохраняется `completedBy`;
- `individual` — у каждого `TaskAssignment` собственные status, comment, timeSpentMinutes и completedAt; задача агрегируется как завершённая после выполнения всеми;
- автор видит прогресс `N/M`, исполнитель — только своё состояние;
- существующие задачи мигрируют в `shared`, чтобы не изменить их поведение задним числом.
