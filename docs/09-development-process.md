# Процесс развития проекта

## Назначение документации

Документация должна помогать выбирать следующую работу и проверять результат. Она не является неизменяемым техническим заданием: решения обновляются после пилотов, но изменения должны быть осознанными и зафиксированными.

## Перед началом итерации

1. Выбрать один измеримый пользовательский результат.
2. Сверить его с целями и текущим этапом roadmap.
3. Проверить фактический код и текущее поведение.
4. Зафиксировать затронутые роли, данные и разрешения.
5. Описать критерии приёмки, ошибочные и пустые состояния.
6. Определить метрику или способ получить обратную связь.

## Формат задачи на доработку

Каждая существенная задача должна содержать:

- проблема и свидетельство;
- пользователь и контекст;
- ожидаемый результат;
- границы и не-цели;
- пользовательский сценарий;
- изменения данных и API;
- права доступа;
- уведомления и побочные эффекты;
- критерии приёмки;
- способ проверки и план отката.

## Definition of Done

Функция считается готовой, когда:

- основной и ошибочный сценарии реализованы;
- сервер проверяет права;
- повторный запрос не создаёт дубль;
- пользователь видит загрузку и результат;
- критические правила покрыты тестами;
- выполнены сборка и проверки типов;
- интерфейс проверен на мобильном размере и в Telegram;
- добавлены необходимые события и измерения;
- обновлена документация;
- изменение проверено владельцем процесса или пилотной группой.

## Работа с обратной связью

Обратную связь следует записывать как наблюдаемую проблему, а не сразу как готовое решение.

Пример:

- наблюдение: «непонятно, что изменится при выборе типа собрания»;
- причина для проверки: форма не показывает состав до сохранения;
- гипотеза: добавить описание типа и предварительный список;
- проверка: пользователь без подсказки создаёт три разных типа собрания.

## Управление решениями

Для значимых решений рекомендуется вести короткий журнал в PR или отдельном ADR:

- дата;
- контекст;
- принятое решение;
- рассмотренные альтернативы;
- последствия;
- условие пересмотра.

Особенно важно фиксировать модель полноты недели, права ответственных, источник истины синхронизации и политику архива.

## Выпуск пилота

Перед пилотом:

- назначить владельца;
- определить участников и период;
- сохранить резервную копию;
- подготовить канал сообщения об ошибках;
- проверить критические сценарии;
- определить, какие метрики собираются.

После пилота:

- собрать фактические обходы и задержки;
- разделить дефекты, UX-проблемы и новые идеи;
- обновить текущий снимок и roadmap;
- не переносить процесс на квиз или концерт, пока базовая модель квеста остаётся неустойчивой.

## Выпуск на продакшен-сервер

Текущий продакшен находится на Selectel VDS в `/opt/megabot` и доступен через `https://megaorgiabot.ru`. Рабочие данные находятся в отдельной Google Sheets базе; deployment-скрипт создаёт проверенный резервный снимок перед перезапуском.

Минимальный порядок обновления:

1. проверить локально `npm run build`;
2. сделать коммит и push в GitHub;
3. зайти на сервер;
4. выполнить резервное копирование Google Sheets базы (`npm run db:sheets:backup`);
5. выполнить `git pull`;
6. выполнить `npm ci`;
7. выполнить `npm run build`;
8. перезапустить процесс `pm2 restart megabot`;
9. проверить логи, сайт и Telegram-сценарий.

Команды описаны подробно в [документе про деплой](./10-deployment-and-operations.md).

Важно: локальная разработка с тем же токеном бота не должна одновременно запускать Telegram long polling. Для локальной проверки интерфейса используйте `DISABLE_TELEGRAM_POLLING=true`.

## Приоритет исправлений

1. потеря или повреждение данных;
2. нарушение прав доступа;
3. невозможность завершить основной сценарий;
4. дубли и неверные уведомления;
5. высокая задержка и непонятное состояние;
6. ошибки интерфейса;
7. улучшения удобства;
8. новые возможности.

## Связь с существующими документами

Корневые `DESIGN.md`, `PRODUCT.md`, `BOT_CHAT_SCENARIOS.md`, `UX_UI_RESEARCH.md` и design-system содержат полезные детальные материалы. Папка `docs` задаёт общий продуктовый вектор. При дальнейшем развитии следует либо синхронизировать корневые документы, либо постепенно заменить их ссылками на актуальные разделы, не удаляя уникальную информацию.

## Регрессионный процесс для Telegram и Sheets — 2026-08-03

Перед выпуском изменений слотов обязательны `npm run lint` и `npm run verify:core`. Fake Telegram должен выдавать монотонно растущие уникальные message ID. Тест обязан пройти stale callback, вход в день, массовый toggle, одиночный toggle, возврат без нового сообщения, сохранение точного массива часов и повторное открытие.

На Selectel после деплоя запускается `npm run sheets:roundtrip-test`. Локальное отсутствие Google-переменных не считается успешной проверкой. Изменения не объявляются production-подтверждёнными, пока health, PM2 logs и server-side round-trip не проверены.

## Повторяющиеся ошибки и профилактика — 2026-08-09

- Разные `Назад`: не добавлять inline-`Назад`; тест проверяет reply-клавиатуру и отсутствие inline-дубля.
- Потеря слотов: UI меняет draft, не availability; перед отменяемым редактированием сохраняется baseline; stale callback и двойное нажатие обязательны в тесте.
- Preview не равен файлу: не поддерживать отдельную CSS-формулу; preview/export вызывают один crop helper, углы проверяет `npm run verify:avatar`.
- Date input выходит за экран: проверять 320 px, `min-inline-size: 0`, `inline-size: 100%`, border-box и WebKit value.
- Изменение глобальной модели задачи без миграции: сначала поле режима и backfill, затем UI и API.
- Успешный build не равен успешному релизу: обязательны `lint`, `verify:avatar`, `verify:core`, production build, health, PM2 logs и серверные Sheets-проверки.
- Изолированный core-тест не должен наследовать production backend: явно ставить `GOOGLE_SHEETS_DATABASE_ENABLED=false`, иначе он попытается загрузить тестовую базу из рабочих Google Sheets.
