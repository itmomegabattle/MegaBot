# Текущее состояние

Дата снимка: **1 августа 2026 года**.

Этот документ описывает фактическое состояние по текущему репозиторию. Он не утверждает, что каждый сценарий уже проверен на реальном Telegram-клиенте и под нагрузкой.

## Техническая основа

- React 19 и TypeScript для Mini App.
- Vite для клиентской сборки.
- Express и единый `server.ts` для API, Telegram long polling, маршрута обработки Telegram updates и серверной логики.
- Локальное JSON-хранилище (`database.json`) как текущее постоянное хранилище.
- Сборка сервера через esbuild.
- Команды `npm run lint`, `npm run build` и `npm run verify:core`.

## Интеграция Google Sheets

Подготовлен двусторонний контур синхронизации слотов доступности:

- серверная авторизация через service account, ключ хранится вне Git;
- запись подтверждённых изменений Mini App в Google Sheets;
- подписанный webhook устанавливаемого Apps Script для изменений из таблицы;
- резервная сверка с таблицей раз в минуту;
- динамическое сопоставление строк по нормализованному имени и постоянному Telegram ID пользователя;
- административная настройка горизонта Mini App от двух до пяти недель и уведомление команды; Google Sheets при этом использует только текущую неделю на листе `ОСНОВА`;
- очистка истёкших недель в понедельник 00:00 по Москве без архива;
- идемпотентное создание отдельного пустого листа-шаблона с сохранением оформления.
- безопасная ротация `ОСНОВА`: резервная копия до изменений, обновление дат, очистка только слот-значений и восстановление чекбоксов; отдельные недельные листы больше не создаются.

До включения в production требуется установить JSON-ключ и переменные окружения на Selectel, подключить Apps Script, создать шаблон через административный endpoint и проверить отчёт сопоставления на боевой `/opt/megabot/database.json`. Подробности: [интеграция Google Sheets](./11-google-sheets-integration.md).

## Известные продуктовые проблемы

### Собрания

- Поля создания требуют проверки и исправления.
- Разница между общим, тематическим и персональным собранием недостаточно очевидна пользователю.
- Нет подтверждённого целевого сценария самостоятельного присоединения к открытому собранию.
- Нет полноценного RSVP-состояния «Я приду» и списка ответов.

### Отмечаемость

- Текущая логика считает сохранение хотя бы одного слота отправкой всей недели: невыбранные часы трактуются как недоступные.
- Это расходится с пожеланием различать частично заполненную и полностью заполненную неделю.
- Подбор собрания должен учитывать обязательных конкретных людей, а не только число доступных участников.
- Нет двусторонней синхронизации со «святой» Google Таблицей.

### Задачи

- Пользователь наблюдал большую задержку при взятии задачи; источник задержки не измерен.
- При завершении фиксируется время, но нет полноценного комментария о результате и причинах отклонения.
- Нужна ясная политика архива вместо ручной очистки рабочего лога.
- Требуется полноценное редактирование опубликованных задач с историей изменений.
- Принудительное назначение частично поддержано логикой создания, но целевой UX и права ответственных необходимо формализовать.
- Нет общего раскрывающегося статуса по каждому исполнителю с двусторонними комментариями.
- Напоминания существуют, но сценарий их создания вместе с ТЗ и быстрая кнопка массового уведомления требуют доработки.

### Интерфейс чата

- Основной принцип динамического сообщения уже используется.
- Общий опыт остаётся фрагментированным и требует проверки на реальных сценариях.
- В качестве продуктового референса указан `https://t.me/ChatGPT5_Midjourney_bot`; изучать нужно механику динамической карточки и быстрых кнопок, а не копировать визуальный стиль.

## Технические риски

- Монолитный `server.ts` усложняет тестирование и независимое развитие доменов.
- JSON-файл ограничивает конкурентные записи, миграции, аудит и надёжную синхронизацию.
- Текущий серверный процесс в продакшене запускается через PM2 как `npm run dev` (`tsx server.ts`), что удобно для быстрого запуска, но менее строго, чем production-запуск собранного `dist/server.cjs`.
- Отсутствие универсального журнала событий блокирует качественную аналитику.
- Не зафиксированы SLO по задержке и доставка/повтор уведомлений.
- Двусторонняя интеграция с таблицами потребует идентификаторов, версий записей и разрешения конфликтов.

## Что считать подтверждённым только после проверки

- корректность всех прав для каждой роли;
- стабильность webhook и уведомлений в реальном окружении;
- производительность операций с задачами;
- визуальная корректность на разных Telegram-клиентах;
- полнота `verify:core` относительно реальных пользовательских путей.

## Подтверждённое состояние на 2026-08-03

- production health endpoint отвечает и сообщает настроенные Telegram, Mini App и Google Sheets;
- адрес Mini App — `https://megaorgiabot.ru`; известные tunnel-домены блокируются в production;
- Telegram UI настраивается при старте и в webhook-режиме, даже если long polling отключён;
- выбор слотов выполняется в одном редактируемом сообщении;
- доступна массовая отметка/очистка дня, обзор показывает `N/8`;
- черновик хранится рядом с состоянием чатовых панелей и переживает рестарт;
- сохранение обновляет `database.json`, после чего ставит экспорт Google Sheets в персистентную очередь;
- fallback-сверка таблицы выполняется раз в минуту после попытки выгрузить ожидающие локальные изменения;
- `verify:core` проверяет уникальные message ID, stale callback, массовый день, возврат, сохранение и повторное открытие.
- обзор недели содержит `Выбрать все слоты`/`Снять все слоты`; callback одного чата сериализуются и защищены от повторной доставки;
- если Telegram не может отредактировать панель, бот отправляет одну восстановленную панель, удаляет старую и продолжает с тем же персистентным черновиком;
- запись базы и sidecar-состояния выполняется через временный файл и атомарное переименование.

Не подтверждено автоматически с локальной машины: production `sheets:roundtrip-test`, поскольку Google-ключ хранится только на Selectel. Его следует запускать после каждого изменения интеграции.
