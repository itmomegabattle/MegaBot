## Ближайшие технические приоритеты

1. **Наблюдаемость интеграций.** Завершить внешний мониторинг, NTP и эксплуатационную приёмку TIME-06/B-11. Admin-only Node diagnostics уже показывают ревизию, очереди и последние результаты; локальная Java diagnostics не подтверждает VDS SLO.
2. **Доставка уведомлений.** Завершить Java/PostgreSQL-паритет очередей и планировщика, включая idempotency, retry, failed/unknown и измеримую точность. Персистентный журнал персональных доставок в Node уже есть; это не завершённый TIME-02…07.
3. **Резервное копирование.** Автоматизировать расписание backup, retention и проверяемое восстановление на тестовом снимке.
4. **Границы релиза.** Развивать действующий Node узкими проверяемыми блоками. Большой Java/PostgreSQL-перенос сохранён отдельно и отложен; незавершённые Java потоки и импорт не включать в Node сборку. Второй чат выполняет только заказанное ревью, без самостоятельных правок и сборок.
5. **Зависимости и безопасность.** Регулярно разбирать `npm audit`, обновлять пакеты отдельными проверяемыми изменениями; CI уже содержит Node/Java jobs и дополняется core/mock/browser проверками. GitHub execution не считать подтверждённым до фактического запуска workflow.

## Задачи: персональное и общее выполнение

Сейчас несколько исполнителей разделяют один статус в явном режиме `shared`; хранится фактический `completedBy`. Планируемое расширение:

- `assignmentMode: shared | individual` выбирается при создании;
- `shared` — текущий режим: одна задача на всех, завершить может любой, хранится `completedBy`;
- `individual` — отдельный `TaskAssignment` со статусом, временем, комментариями и `completedAt` для каждого;
- автор видит прогресс `N/M`, исполнитель — своё назначение;
- старые задачи уже читаются как `shared`, но для старого выполнения `completedBy` не выдумывается;
- после первого изменения статуса режим нельзя менять: создаётся новая задача.

Правила переоткрытия отдельного назначения и частичного выполнения закреплены
в B-12: исполнитель либо администратор, индивидуальная история без завершения
чужих назначений. Это ещё не реализованная production-функция.

## Процессы мероприятий

Следующий продуктовый слой — повторно используемые шаблоны:

`мероприятие → блок → процесс → задача → чек-лист → исполнитель → результат`.

Шаблон должен хранить зависимости, относительные дедлайны, роли и чек-листы. Его нельзя строить только автоматическим импортом старой доски: сначала владелец процесса описывает реальный ход подготовки, затем команда проводит ограниченный пилот.

Предлагаемый порядок пилотов:

1. квест;
2. квиз;
3. гала-концерт с несколькими представлениями ответственности.

## Аналитика после появления истории

- выполнение до дедлайна и план/факт времени;
- нагрузка по людям, блокам и неделям;
- полнота слотов и посещаемость встреч;
- качество повторного использования чек-листов;
- история ролей и областей ответственности.

Метрики должны улучшать процесс, а не создавать скрытый рейтинг людей. Для них нужен событийный журнал создания, назначения, статусов, дедлайнов, RSVP и недельных снимков доступности.

## Решение о смене архитектуры

Перенос теперь задан требованиями пользователя: React сохраняется, backend — Spring MVC, БД — PostgreSQL. Он уже не условная возможность «когда-нибудь при росте». Дополнительные технические основания:

- требуется несколько одновременно работающих серверных экземпляров;
- полноснимочная запись приближается к квотам или заметно задерживает действия;
- нужны транзакции между сущностями и гарантированная очередь доставки;
- история и аналитика становятся существенно больше текущего состояния;
- восстановление и конфликтные изменения перестают надёжно проверяться digest-снимком.

До переключения Node/Sheets использует проверенную сериализацию mutations, optimistic versions и durable recovery journal (DATA-01/02); несколько Node-писателей по-прежнему не поддерживаются. Пользовательская таблица слотов сохраняется как интеграция, закрытая Sheets database после cutover — только архив. Подробные этапы и критерии находятся в backend.md, здесь их не дублируем.

## Definition of Done для следующей функции

- описаны основной, пустой и ошибочный сценарии;
- сервер проверяет права и повторный запрос не создаёт дубль;
- данные переживают рестарт и сбой внешней интеграции;
- есть автоматическая регрессия и профильная проверка;
- интерфейс проверен на мобильном Telegram-клиенте;
- известен план отката;
- соответствующий документ обновлён без создания нового дублирующего `.md`.
