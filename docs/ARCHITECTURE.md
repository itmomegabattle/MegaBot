# Архитектура, данные и интеграции

## Контур приложения

```text
Telegram clients
      │
      ├── Bot API polling или защищённый webhook — один выбранный режим
      └── Mini App HTTPS
               │
        Caddy → Express (`server.ts`)
                    ├── React/Vite client
                    ├── Google Sheets database
                    ├── Google Sheets availability
                    └── Google Calendar
```

Один Node.js-процесс обслуживает API, статическую Mini App, Telegram updates, уведомления и фоновые синхронизации. Горизонтальное выполнение нескольких экземпляров не поддерживается: Telegram consumer и полноснимочная запись базы рассчитаны на одного писателя.

Наблюдаемость разделяет `/api/health/live` и `/api/health/ready`: первый отвечает за живой процесс, второй — за способность надёжно принять mutation. Ошибка durable-записи даёт readiness `503`; отстающая Sheets replication имеет состояние `degraded`, пока подтверждённая ревизия защищена локальным recovery journal. Совместимый `/api/health` отражает readiness. Admin-only `/api/admin/diagnostics` агрегирует ревизии, очереди и их возраст, worker heartbeat и безопасные последние ошибки. API выдаёт correlation headers `X-Request-ID` и `X-Operation-ID`; структурированные error-события связывают их с `deliveryId` без раскрытия токенов.

## Код

- `server.ts` — Express, Telegram, права, фоновые процессы и координация интеграций;
- `src/components/MiniApp.tsx` — основная пользовательская поверхность;
- `src/types.ts` — доменные типы;
- `src/stateMaintenance.ts` — очистка и перенос состояния;
- `src/availabilityConfig.ts` — календарный горизонт слотов;
- `src/googleSheetsDatabase.ts` — постоянное хранилище;
- `src/googleSheetsSync.ts` — пользовательская таблица доступности;
- `src/googleCalendarSync.ts` — календарные события;
- `scripts/verify-*` — автономные регрессионные проверки.

Сервер собирается в `dist/server.cjs`, клиент — в версионированные файлы `dist/assets`.

## Авторизация и безопасность API

Mini App отправляет Telegram `initData`. Сервер проверяет подпись, окно `auth_date` 5 минут с допуском 30 секунд вперёд и берёт identity только из подписанного `user`. Непрозрачная HttpOnly/Secure cookie живёт до 30 дней; её hash находится в отдельном серверном реестре, поэтому повторный вход, logout и деактивация пользователя отзывают прежнюю сессию. `SESSION_SECRET` независим от bot token. Большинство `/api` маршрутов требует сессию; actor-поля `requesterId`, `creatorId`, `hostId` и self-service `userId` принудительно заменяются ID из неё, поэтому body не даёт чужих прав.

Участники деактивируются, а не удаляются физически: профиль остаётся для авторов, организаторов, исполнителей и комментариев в истории, но больше не участвует во входе, рассылках, подборе встреч и новых назначениях. Нельзя деактивировать последнего активного администратора. Незавершённые задачи освобождаются только после отдельного подтверждения, а будущие встречи сначала требуют сменить организатора. При загрузке состояния сервер выводит полный отчёт orphan-ссылок вместо их молчаливого удаления.

Создающие API для участников, faculty-задач, встреч, обычных задач и рассылок принимают `Idempotency-Key` из 8–128 безопасных символов. Область ключа — подтверждённый actor; запись содержит operation и SHA-256 канонического JSON body. Первый запрос резервирует ключ до изменения данных, завершённый ответ сохраняется в основном state и переживает restart. Точный повтор возвращает исходные status/body с `Idempotency-Replayed: true`; другой body или route под тем же ключом получает `409`. Одновременные повторы в процессе ждут первый запрос. Mini App генерирует UUID-ключ и при транспортной ошибке делает один retry с тем же значением. Отсутствующий заголовок временно допускается только для совместимости с уже открытыми старыми клиентами; Spring/PostgreSQL реализация должна сделать его обязательным и хранить уникальность в БД.

`/api/state` — временный frontend-адаптер только для core team. Он возвращает явный DTO без Telegram ID, служебной конфигурации и чужих сообщений; год рождения виден только самому пользователю и администратору. Факультетская сессия не имеет доступа к общему state, экспорту, интеграционным ссылкам и core mutations: ей разрешены только `/api/faculty/me`, `/api/faculty/my-tasks` и logout. Назначения фильтруются одновременно по assignee и faculty scope.

Клиентский boot — явная машина состояний, а не проверка `state === null`: `loading`, `ready`, `telegram-required`, `unauthorized`, `forbidden`, `external-only`, `offline`, `unavailable`. Boot-запросы имеют timeout 12 секунд и общий `AbortController`, который отменяется при повторе и размонтировании.

Входные meeting/task DTO проверяются на сервере до мутации: существующая календарная дата, время `ЧЧ:ММ`, конечные числовые диапазоны, enum, типы и размеры массивов, ограничения текста и ID. Ошибка имеет `400` и поля `{message, fieldErrors, serverNow}`; невалидная команда не сохраняется и не запускает внешние уведомления. HTTP-валидация не полагается на ограничения формы Mini App.

Критические переходы задач и правила времени встреч вынесены в общие доменные команды, которые вызывают и HTTP, и Telegram. Последний шаг диалога повторно загружает актуальное состояние: старая кнопка не может оживить отменённую или завершённую задачу, а комментарий не завершает задачу после её отмены. Команды навигации распознаются до свободного текста формы и отменяют незавершённый чат-черновик. Создание обычной встречи из чата использует те же ограничения активных дней и часов, что Mini App; `vibe` сохраняет отдельное правило времени.

Аудитории каналов вычисляет общий `audiencePolicy`. `all` для обычных встреч, задач и рассылок означает только активную основную команду (`admin/organizer`), faculty-задачи ограничены активными ответственными выбранного факультета. При создании встречи сохраняется snapshot `audienceUserIds`; новые пользователи не добавляются к старому приглашению автоматически. Этот снимок одновременно определяет Telegram-уведомления, право RSVP, отображение в Mini App и список в описании Google Calendar. Legacy-встречи получают снимок при нормализации, а Sheets database хранит его отдельными строками `meeting_participants.kind=audience`.

Пользовательские Telegram-уведомления записываются до сетевого вызова в единый `notificationDeliveries`-журнал основного state. Запись относится к одному адресату, содержит immutable payload, dedupe key, intended/available time, lease, попытки и результат Bot API. Worker отправляет последовательно вне мутации БД: `429` переносит только адресата на `retry_after`, `403` становится `failed`, сетевой таймаут — `unknown` без автоматического повтора, успешный ответ сохраняет `message_id`. После restart подхватываются только `planned/retry` и истёкшие leases; `sent/failed/unknown` не дублируются. Для задач сохраняется `disable_notification`, для IMPORTANT — `message_thread_id`. Старый `pendingImportantNotifications` мигрирует без прежней обрезки до 100 записей. Admin API и Mini App показывают сводку и позволяют повторить выбранные `failed/unknown`. Это надёжный Node-контур немедленных уведомлений, но не будущий PostgreSQL scheduler отложенных рассылок TIME-02…TIME-07.

Входящие Telegram updates проходят через персистентный `telegramInbox` с уникальным `update_id`, статусами, временем следующей попытки и lease. Webhook подтверждает update после записи, а polling двигает offset после записи всей пачки. Worker сохраняет порядок внутри одного чата, не блокирует другие чаты ошибкой, возобновляет retry и истёкшие leases после restart и не запускает завершённый `update_id` повторно. Это гарантия для единственного Node-писателя; общая транзакция inbox, доменной мутации и outbox при нескольких экземплярах относится к B-08/PostgreSQL.

Публичны вход и подписанный webhook Google Sheets. Telegram HTTP router доступен только в режиме `webhook` и до разбора JSON проверяет отдельный `X-Telegram-Bot-Api-Secret-Token`; в режимах `polling`/`disabled` он отвечает 404. Публичной настройки webhook нет — используется эксплуатационная CLI-команда. Вход имеет лимиты по IP и Telegram ID, рассылки — по actor, числу запросов и получателей. Cookie-auth mutations требуют same-origin `Origin`; production не запускается с `ALLOW_LOCAL_PREVIEW=true`. UI защищён CSP, разрешающим локальные ресурсы, официальный Telegram SDK и Telegram frame ancestors. Секреты и `initData` не логируются; runtime-файлы исключены из Git. JSON body ограничен 1 MB.

## Основная база

Production-данные реплицируются в закрытую Google-таблицу с версией схемы `11`. Перед успешным ответом на mutation приложение синхронно и атомарно добавляет неизменяемую ревизию в локальный recovery journal, затем объединяет частые изменения в последовательную очередь снимков Sheets. При старте выбирается самая новая проверенная ревизия из Sheets со статусом `ready` и локального журнала; более новая локальная ревизия повторно выгружается в Sheets.

Листы схемы:

- служебные: `meta`, `snapshot`, `settings`, `audit_log`;
- команда: `users`, `user_avatars`, `faculties`;
- мероприятия: `events`;
- доступность: `availability_weeks`, `availability_slots`;
- встречи: `meetings`, `meeting_participants`;
- задачи: `tasks`, `task_assignees`, `task_comments`, `task_reminders`, `task_log`;
- внутренние уведомления: `bot_messages`.

`snapshot` нужен для восстановления, нормализованные листы — для проверки и чтения, `task_log` — для человека. `database.json` используется только при отключённой Google Sheets database и не является production-хранилищем. `chat-panels.json` содержит панели/черновики, наблюдаемый состав групп и pending экспорты слотов: его нельзя целиком отбросить как неважный временный файл при миграции.

Изменения задач выполняются в синхронной секции `load → проверка прав/версии → узкое изменение → save`; Telegram вызывается только после фиксации. Поля `task.version`, `assignmentMode` и `completedBy` хранятся в Sheets. Доступность использует `weekVersions` по календарному `weekStart`; Sheets database schema 11 хранит их в `availability_weeks.week_versions_json`. Две правки одной версии одной сущности дают один успех и один `409`. Это временная сериализация внутри единственного Node-процесса до транзакций PostgreSQL.

В Sheets-режиме сохранение увеличивает `databaseRevision` и подтверждается только после `fsync` локальной записи recovery journal. Ошибка локальной записи возвращает `503`; недоступность Sheets оставляет подтверждённую ревизию в очереди репликации. SIGTERM/SIGINT прекращает новые HTTP-mutations и ограниченно ожидает выгрузку; если Sheets недоступна, журнал остаётся recovery-путём следующего запуска. Это временная гарантия одного Node-процесса до PostgreSQL: каталог журнала должен находиться на постоянном диске и входить во внешние резервные копии.

## Таблица доступности

Mini App сохраняет одну календарную неделю через `POST /api/availability`: `{weekStart, days, hardUnavailableDays, out, expectedVersion}`. Сервер перечитывает свежий aggregate, проверяет версию именно этой даты и заменяет только семь её дней. Full-replace формат намеренно отклоняется с `409`, чтобы старый клиент не мог стереть другую неделю. Локальные черновики и Telegram flow фиксируют baseline по дате; обновление состояния не затирает dirty-недели.

Отдельная пользовательская таблица использует один рабочий лист `ОСНОВА`. Сервер строит в нём все настроенные 2–5 недель, активные дни и часы. При изменении календарной недели или layout сначала обновляется единственная резервная вкладка `РЕЗЕРВ ОСНОВА`; старые вкладки `Неделя …` скрываются.

Привязка строки пользователя хранится через Telegram ID в developer metadata. Номер строки не считается постоянным, поэтому сортировка таблицы не должна связывать чужие слоты. Первичное сопоставление выполняется по безопасно нормализованному ФИО; неоднозначные совпадения не записываются автоматически.

Направления синхронизации:

- Mini App/Telegram → немедленный экспорт; при ошибке пользователь остаётся в персистентной очереди;
- таблица → устанавливаемый Apps Script trigger отправляет подписанный HTTPS webhook;
- страховочная сверка выполняется не чаще чем раз в 30 секунд с backoff после ошибки;
- открытие Mini App может инициировать сверку с коротким TTL.

Импорт старой недели защищён от календарного сдвига, но общего версионированного разрешения конфликтов нет. `mergePrimarySheetAvailability` применяет все фактически представленные даты до пяти недель; отсутствующий столбец сохраняет прежний день. Полный future-week round-trip остаётся открытым (DATA-04): checkbox без отдельного статуса не различает «не отметил» и «не смогу», необходимы отдельный out каждой недели и явный stale-конфликт. Экспорт нескольких недель не доказывает двусторонний паритет.

## Google Calendar

MegaBot односторонне синхронизирует `meeting`, `setup` и `vibe` в календарь `ITMO MEGABATTLE` с часовым поясом `Europe/Moscow`.

Событие содержит название, тип, дату, время, длительность, тему/описание, формат, организатора, приглашённых и внутренний MegaBot ID. RSVP хранится как `yes/no`, отсутствие ключа означает `unanswered`; `attendeeIds` остаётся совместимым производным списком ответов `yes`. Список RSVP в Calendar не записывается. Если длительность отсутствует или некорректна, используется один час. Позднее событие корректно заканчивается на следующую дату.

Создание и изменение обновляют одно событие по стабильному ID; отмена удаляет его. При временной ошибке используется очередь повтора и стартовая сверка. Успешная mutation в Sheets-режиме означает durable recovery record, но не завершённую синхронизацию Google Calendar; успешный mock-тест не подтверждает живой календарь или доставку уведомлений.

## Фоновые процессы

Календарный контракт проекта — `Europe/Moscow`. Date-only дедлайн преобразуется в instant конца дня МСК, встреча — в instant выбранных даты и времени МСК; парсинг проверяет реальное существование календарной даты. `/api/state`, faculty boot endpoints и `/api/health` возвращают `serverNow` и `timeZone`. Эти вычисления не используют локальную TZ ОС или браузера.

Удаление задач разделено на две административные операции. Archive clear удаляет только `completed/cancelled` после сверки preview ID. Season reset удаляет все задачи только после preview и точной фразы подтверждения. Перед обеими операциями синхронно записывается recovery-record; legacy endpoint полной очистки отключён.

Telegram-планировщики запускаются отдельно от update transport: режимы `polling`, `webhook` и `disabled` влияют только на получение updates. Для фактической отправки по расписанию всё равно необходим bot token.

- Telegram updates: один режим `polling`, `webhook` или `disabled`; оба входных транспорта сначала сохраняют update в durable inbox, обработчик работает отдельно;
- снимок основной базы: debounce 500 ms, повтор через 5 секунд;
- ротация недель: раз в минуту и при чтении состояния;
- таблица доступности: push-webhook плюс периодическая сверка;
- структура `ОСНОВА`: проверка раз в час;
- Calendar: полная сверка при старте, очередь ошибок — раз в минуту;
- задачи и дни рождения: раз в 15 минут;
- очередь топика «ВАЖНОЕ»: раз в минуту с увеличивающейся задержкой.

## Целевая архитектура

React остаётся клиентом; Spring MVC в одном Spring Boot приложении заменит Express/Node бизнес-логику, PostgreSQL — Sheets database. Доменные API, очередь и отдельные Telegram-сценарии уже реализованы и проверяются локально. Google-интеграции, полный Telegram-паритет и миграция ещё не завершены; production работает на Node. Пользовательская Sheets остаётся внешним интерфейсом доступности. Модель, baseline 54 Node-маршрутов, тесты и release gates описаны в [backend.md](../backend.md).
