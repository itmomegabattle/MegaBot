# Архитектура, данные и интеграции

## Контур приложения

```text
Telegram clients
      │
      ├── Bot API long polling
      └── Mini App HTTPS
               │
        Caddy → Express (`server.ts`)
                    ├── React/Vite client
                    ├── Google Sheets database
                    ├── Google Sheets availability
                    └── Google Calendar
```

Один Node.js-процесс обслуживает API, статическую Mini App, Telegram updates, уведомления и фоновые синхронизации. Горизонтальное выполнение нескольких экземпляров не поддерживается: Telegram long polling и полноснимочная запись базы рассчитаны на одного писателя.

## Код

- `server.ts` — Express, Telegram, права, фоновые процессы и координация интеграций;
- `src/components/MiniApp.tsx` — основная пользовательская поверхность;
- `src/types.ts` — доменные типы;
- `src/stateMaintenance.ts` — очистка и перенос состояния;
- `src/availabilityConfig.ts` — календарный горизонт слотов;
- `src/googleSheetsDatabase.ts` — постоянное хранилище;
- `src/googleSheetsSync.ts` — пользовательская таблица доступности;
- `src/googleCalendarSync.ts` — календарные события;
- `scripts/verify-*` — автономные регрессионные проверки.

Сервер собирается в `dist/server.cjs`, клиент — в версионированные файлы `dist/assets`.

## Авторизация и безопасность API

Mini App отправляет Telegram `initData`. Сервер проверяет подпись токеном бота и выдаёт HttpOnly/Secure cookie `megabot_session` на 30 дней. В production почти все `/api` маршруты требуют эту сессию; переданные клиентом поля идентичности заменяются сервером на ID авторизованного пользователя.

Публичными остаются только вход через Telegram, Telegram webhook/router, настройка webhook и подписанный webhook Google Sheets. Секреты хранятся в `.env` и `/opt/megabot/secrets`, никогда не коммитятся. JSON body ограничен 1 MB.

## Основная база

Production-источник истины — закрытая Google-таблица с версией схемы `8`. Приложение читает только согласованный снимок со статусом `ready`, держит очищенную копию в памяти и объединяет частые изменения в последовательную очередь снимков.

Листы схемы:

- служебные: `meta`, `snapshot`, `settings`, `audit_log`;
- команда: `users`, `user_avatars`, `faculties`;
- доступность: `availability_weeks`, `availability_slots`;
- встречи: `meetings`, `meeting_participants`;
- задачи: `tasks`, `task_assignees`, `task_comments`, `task_reminders`, `task_log`;
- внутренние уведомления: `bot_messages`.

`snapshot` нужен для точного восстановления, нормализованные листы — для проверки и чтения, `task_log` — для человека. `database.json` используется только как локальный fallback при отключённой Google Sheets database и не является production-хранилищем. `chat-panels.json` содержит только transient-состояние Telegram-панелей, очередей и черновиков.

Каждое сохранение увеличивает `databaseRevision`. Асинхронные сохранения встреч объединяются так, чтобы устаревший ответ внешнего API не затёр более новое изменение.

## Таблица доступности

Отдельная пользовательская таблица использует один рабочий лист `ОСНОВА`. Сервер строит в нём все настроенные 2–5 недель, активные дни и часы. При изменении календарной недели или layout сначала обновляется единственная резервная вкладка `РЕЗЕРВ ОСНОВА`; старые вкладки `Неделя …` скрываются.

Привязка строки пользователя хранится через Telegram ID в developer metadata. Номер строки не считается постоянным, поэтому сортировка таблицы не должна связывать чужие слоты. Первичное сопоставление выполняется по безопасно нормализованному ФИО; неоднозначные совпадения не записываются автоматически.

Направления синхронизации:

- Mini App/Telegram → немедленный экспорт; при ошибке пользователь остаётся в персистентной очереди;
- таблица → устанавливаемый Apps Script trigger отправляет подписанный HTTPS webhook;
- страховочная сверка выполняется не чаще чем раз в 30 секунд с backoff после ошибки;
- открытие Mini App может инициировать сверку с коротким TTL.

Разрешение конфликтов — последнее подтверждённое изменение. Импорт начатый для старой недели не применяется после календарного сдвига.

## Google Calendar

MegaBot односторонне синхронизирует `meeting`, `setup` и `vibe` в календарь `ITMO MEGABATTLE` с часовым поясом `Europe/Moscow`.

Событие содержит название, тип, дату, время, длительность, тему/описание, формат, организатора, приглашённых и внутренний MegaBot ID. Список подтвердивших RSVP в Calendar не записывается. Если длительность отсутствует или некорректна, используется один час. Позднее событие корректно заканчивается на следующую дату.

Создание и изменение обновляют одно событие по стабильному ID; отмена удаляет его. Если Google временно недоступен, встреча уже остаётся в основной базе, попадает в очередь повтора и сверяется при старте процесса.

## Фоновые процессы

- Telegram `getUpdates`: long polling с повтором после сетевой ошибки;
- снимок основной базы: debounce 500 ms, повтор через 5 секунд;
- ротация недель: раз в минуту и при чтении состояния;
- таблица доступности: push-webhook плюс периодическая сверка;
- структура `ОСНОВА`: проверка раз в час;
- Calendar: полная сверка при старте, очередь ошибок — раз в минуту;
- задачи и дни рождения: раз в 15 минут;
- очередь топика «ВАЖНОЕ»: раз в минуту с увеличивающейся задержкой.

## Проверки

| Команда | Что проверяет |
|---|---|
| `npm run lint` | TypeScript без генерации файлов |
| `npm run build` | production-сборку клиента и сервера |
| `npm run verify:core` | Telegram-сценарии, права, задачи, встречи, слоты, напоминания |
| `npm run verify:availability` | ротацию и метаданные календарных недель |
| `npm run verify:birthdays` | даты, дедлайн, повторы и реквизиты дней рождения |
| `npm run verify:avatar` | одинаковую геометрию preview и сохранённого crop |
| `npm run verify:sheets` | layout и round-trip логики `ОСНОВА` на mock API |
| `npm run verify:database-sheets` | схему, снимки и очистку основной базы |
| `npm run verify:calendar` | Calendar payload, время, обновление, удаление и восстановление |

Тесты используют fake Telegram и fake Google API и не должны наследовать production-секреты. Реальные server-side проверки выполняются отдельно по инструкции эксплуатации.
