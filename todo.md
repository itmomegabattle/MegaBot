## 1. Как выполнять этот файл

Исполнитель: в том числе GPT-5.6 Sol. Не пытайся реализовать весь файл за один проход.

1. Прочитай `README.md`, `docs/PRODUCT.md`, `docs/ARCHITECTURE.md`, `docs/OPERATIONS.md`, затем этот файл. Дизайн находится в `todo_design.md`, целевой Java-бэкенд — в `backend.md`.
2. Выбери первый незавершённый пункт с выполненными зависимостями. В начале работы назови его ID. Один пункт — одна проверяемая порция изменений.
3. Найди указанные функции через `rg`: номера строк относятся к проверенной ревизии и могут сместиться. Сначала воспроизведи дефект на синтетических данных, затем исправляй.
4. После изменения выполни критерии готовности пункта и подходящие регрессионные проверки. Отметь `[x]` только после проверки; допиши дату, результат и изменённые файлы непосредственно под пунктом.
5. Сохраняй чужие изменения. Не используй production-токен/таблицу/календарь для тестов. Не отправляй настоящие рассылки. Деплой, массовое удаление и перенос production-данных не входят в выполнение отдельного пункта без запроса владельца.
6. При смене API обновляй всех потребителей: Mini App, Telegram, синхронизации, тесты и документацию. Исправление только кнопки не закрывает серверную проблему.
7. Не делай большое разбиение Node-сервера параллельно с переносом на Java. Срочные ошибки исправляются в текущем коде; долговременная архитектура реализуется один раз по `backend.md`.
8. Каждый пункт выполнять с Ponytail (`full`) по `AGENTS.md`: переиспользовать готовое, сокращать дублирование и лишний код без ухудшения читаемости, безопасности и полноты тестов. Требования пункта не урезать ради числа строк.

Приоритеты: **P0** — обход доступа/необратимая потеря данных; **P1** — нарушение основного сценария или надёжности; **P2** — поддерживаемость, неудобство, эксплуатационный риск; **P3** — улучшение после основных работ. «Код» означает подтверждённое поведение реализации, но не обязательно наблюдавшийся production-инцидент. «Локально» означает воспроизведение на изолированном экземпляре.

## 4. Безопасность и разграничение доступа

### [x] SEC-01 · P0 · Вход позволяет подменить подписанного пользователя

**Доказательство:** `server.ts:223` (`verifyTelegramInitData`) возвращает только boolean; `/api/user/get-or-create` около строки 2640 затем выбирает пользователя по `telegramId` и `username` из JSON body. Подписанные `initData` участника 102 + отдельные поля администратора 101 дали HTTP 200, `user.id=audit-admin`, `role=admin`. Реальных аккаунтов в проверке не было.

**Сделать:** возвращать из валидатора проверенный объект Telegram user; брать ID/username исключительно из него. Удалить поля идентичности из клиентского контракта либо игнорировать их. Проверять наличие и тип `user.id`, запретить дубли ключей query string, неверные hash/JSON. Админские права привязывать к неизменяемому Telegram ID, а не владению username. Удалить неявный fallback `@wonkersone`; предусмотреть явную bootstrap-конфигурацию ID администратора.

**Готово:** корректный вход работает; подписанный обычный участник с любыми чужими body-полями никогда не получает чужой профиль/сессию; неподписанные и неизвестные пользователи получают 403; переименование username не передаёт права. Тесты проверяют также автоматическое первичное связывание уже добавленного человека и отсутствие дубликата Telegram ID.

**Выполнено 21.09.2026:** `verifyTelegramInitData` возвращает только проверенного пользователя из подписанного payload, отклоняет неверный hash, malformed `user`, некорректный `user.id` и дубли query-параметров. `/api/user/get-or-create` больше не принимает identity из JSON body; Mini App отправляет только `initData`. Bootstrap администратора использует только `ADMIN_TELEGRAM_IDS`, username fallback удалён. Первичное связывание допускает ровно одно совпадение и не создаёт второй Telegram ID. Изменены `server.ts`, `src/App.tsx`, `scripts/verify-core-flows.mjs`, `docs/OPERATIONS.md`. Проверки: `npm run lint`, `npm run verify:core`, `git diff --check` — успешно. Production и реальные аккаунты не проверялись; TTL `auth_date`, отзыв и ротация сессий остаются в SEC-03.

### [x] SEC-02 · P0 · Открытые Telegram webhook и setup-webhook

**Доказательство:** публичные исключения middleware около `server.ts:903`; обработчики около 2700/2729. Без cookie и секрета поддельное сообщение `/bindteamchat` от синтетического admin изменило `teamChatId` на `-999`. Публичный GET `/api/setup-webhook` вызвал `setWebhook` на mock API.
